## 原始需求

用户要求分析项目现有 `docs/` 文档，并给出当前程序的软件开发规划。项目目标是快速完成一个本机使用的 macOS HUD，通过 Codex 用户级 Hooks 同时跟踪 Codex CLI 与 Codex 桌面客户端中的多个会话。

用户随后提供 HUD 草图。草图表达的核心布局为：左侧 Agent 图标、中间当前会话标题、右侧固定红黄绿三个状态灯。菜单栏保留一个应用图标，点击后可显示菜单并打开独立设置窗口；HUD 本身是应用主要展示界面。

用户明确说明：仓库已有两份历史规划只作为开发基础和参考，不是必须照搬的规范。历史文档与本次讨论冲突时，以用户最新需求、本讨论纪要和对应 PRD 为准。

## 仓库与资料审查结论

- 当前仓库只有 `README.md` 和两份历史规划，没有程序代码、工程文件或测试。
- Codex Hooks 路线可行，官方支持本项目需要的 `SessionStart`、`UserPromptSubmit`、`PermissionRequest`、`PostToolUse`、`Stop`、`Interrupt`、`SessionEnd` 事件。
- Codex 可同时加载多个 Hook 来源；本项目最终选择修改用户级 `~/.codex/hooks.json`，不采用插件内置 Hooks。
- `SessionEnd` 始终同步执行；历史文档中“所有 Hook 都设置为异步”不准确。
- 历史文档中的轮播、乱序处理、代码样例和“加密 Socket”等内容存在冲突或不可直接编译的问题，PRD 已重新定义。
- 官方事实参考：[OpenAI Hooks 官方文档](https://learn.chatgpt.com/docs/hooks)。

## 完整问答记录

### 1. 首版支持范围

**问题：** 首版是否限定支持 Codex CLI 和 Codex 桌面客户端，不支持普通 ChatGPT 桌面对话？
**用户回答：** 确认。两者走同一套 Codex Hooks，首版适配压力较小，目标是尽快看到结果。

### 2. MVP 最小闭环

**问题：** 是否将 MVP 限定为悬浮 HUD、多会话状态灯、Hooks 实时转发和基本轮播，暂不做历史系统、复杂设置、自动安装包和跨平台？
**用户回答：** 确认。

### 3. HUD 与应用窗口结构

**问题：** 是否采用菜单栏图标、下拉菜单、独立设置窗口和悬浮 HUD，不开发传统主窗口？
**用户回答：** 确认，并提供草图作为大致参考。HUD 是主展示界面。

### 4. 标题来源

**问题：** Hooks 没有稳定的官方“对话标题”字段时，标题如何生成？
**用户回答：** 能从对话取得则使用对话信息；不能取得则使用项目最后一级目录名；也可组合二者。当前先采用该方式，未来有更好来源再优化。

### 5. 标题降级顺序

## 最终共同理解

Traceflow MVP 是一款 macOS 14+ 本机菜单栏应用。它通过用户主动安装到 `~/.codex/hooks.json` 的旁路 Hook，将 Codex CLI 与 Codex 桌面客户端事件交给短生命周期转发器，再经本地 Unix Domain Socket 送入常驻 App。App 维护会话状态和全局轮播，在一个不抢焦点、可跨显示器拖动的 `420 × 44 pt` 悬浮 HUD 中显示 Codex 图标、单行会话标题和红黄绿状态灯。

MVP 优先验证双端 Hooks、状态机、轮播与 HUD 体验。会话不会自动删除，用户在设置页用复选框决定哪些会话参与轮播。所有待机会话仍继续轮播。运行状态不跨重启保存，对话摘要只存内存。数据库、安装包、公证、跨平台、通知、声音、HUD 点击交互和复杂会话管理均延后。

实现阶段必须先完成真实 Hooks PoC。若 Codex 桌面端无法产生所需事件，应停止并与用户讨论，不得自行将双端 MVP 改成 CLI-only。
