# Traceflow 项目分组与会话管理讨论纪要

## 原始需求

用户在测试会话同步后发现约一百多个历史会话全部默认启用，导致无用历史会话也参与 HUD 轮播；逐项关闭操作成本过高。同时，当前设置页将所有项目和会话放在同一个一级列表中，层级不清晰。

用户希望：

1. 设置页改为二级结构，第一层为项目，第二层为该项目包含的会话。
2. 所有同步会话初始为关闭状态，由用户主动启用。
3. 提供适合大量会话的快速管理方式。

## 问答记录

### 问题 1：现有测试数据如何处理

当前已经同步的会话均为启用状态。是否需要为现有记录设计迁移规则？

推荐答案：开发测试阶段可不做历史数据迁移，重新安装或重新同步即可验证新规则。

用户回答：当前为开发测试阶段，不必考虑历史数据；重新安装后可以覆盖，或者重新进行会话同步。

### 问题 2：Hook 实时发现的新会话是否默认关闭

除了同步导入的历史会话，Hook 实时发现的新会话是否也统一默认关闭？

推荐答案：全部新发现会话都默认关闭，使“参与 HUD”始终由用户主动决定。

用户回答：确认。另补充，Hook 实时发现的新会话应排到当前列表顶部，或所属项目的会话列表顶部。

### 问题 3：新会话是否同时将项目置顶

采用项目二级分组后，Hook 实时发现的新会话排到所属项目内部顶部时，是否同时将所属项目分组移动到项目列表顶部？

推荐答案：会话和项目同时置顶，但不自动展开项目，也不自动启用 HUD。

用户回答：确认。

### 问题 4：项目默认展开还是折叠

同步大量会话后，项目分组的默认展开状态如何处理？

推荐答案：项目默认折叠，只恢复用户上次手动展开的项目，并持久化展开状态。

用户回答：确认。

## 代码与交互核验

- 当前同步导入新会话时使用 `PersistedSession` 的默认值，导致 `isIncludedInHUD` 为 `true`。
- Hook 创建新会话时也使用同一默认值，因此同样会自动参与 HUD。
- 当前设置页直接遍历全部会话，没有项目分组和批量选择能力。
- HUD 调度器已只轮播 `isIncludedInHUD == true` 的会话，因此无需修改状态优先级与公平轮播算法。
- 会话已经保存完整项目路径和项目名称，可以用标准化完整路径作为稳定分组键，避免同名但不同目录的项目被错误合并。
- UI/UX 核验建议长列表采用分层披露和批量操作；SwiftUI 设置页继续使用原生 `Form`、`Section` 和披露控件。

## 最终共同理解

1. 设置页会话区域改成“项目 → 会话”二级结构。
2. 项目以标准化完整项目路径为身份；界面主要显示项目名称，同时显示路径、会话数和已启用数。
3. 项目行提供整组启用与整组关闭，解决大量会话逐项操作的问题；会话行仍可单独勾选。
4. 同步导入和 Hook 实时发现的所有新会话均默认关闭，不参与 HUD。
5. 用户主动启用后才加入 HUD 轮播，关闭后立即退出轮播。
6. 项目默认折叠，用户展开状态按项目持久化。
7. Hook 实时发现的新会话排到所属项目内部顶部，所属项目同时移到项目列表顶部。
8. Hook 新会话置顶不自动展开项目，也不自动启用会话。
9. App Server 批量同步不将全部历史项目反复置顶；同步结果采用稳定排序。
10. 当前开发测试阶段不实现旧数据迁移，允许清空记录或重新同步验证新行为。
