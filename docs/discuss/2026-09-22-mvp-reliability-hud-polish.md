# Traceflow MVP 可靠性修复与 HUD 视觉优化讨论纪要

> 历史记录：本文中的黄绿灯含义和轮播规则已由 [最新讨论](../discuss/2026-09-23-carousel-priority-color-timing.md) 与 [正式 PRD](../plan/2026-09-23-carousel-priority-color-timing.md) 覆盖。当前规则为黄灯已完成、绿灯运行中，红 > 黄 > 绿三级抢占。

## 原始需求

用户要求在继续开发前，先审查当前阶段已经实现的全部功能逻辑，找出遗漏、未完成和实现不可靠之处，再使用 `grill-me` 逐项讨论并整理为可执行的修复方案。

审查背景与约束：

1. 当前仍是 MVP，优先验证核心功能和实现路径，不引入数据库，也不提前增加高级选项。
2. 历史规划文档仅作为开发基础；本次讨论形成的新结论覆盖历史文档中的冲突内容。
3. 最终 PRD 会交给低智能编码模型执行，因此必须明确状态、数据流、错误处理、界面行为、测试输入输出和验收标准。
4. 本轮只形成讨论纪要与 PRD；获得用户明确批准后才能修改程序代码。

## 审查发现

### 高优先级

1. `sessions.json` 解码失败后，应用虽然记录错误，但仍允许后续 Hook 调用保存逻辑；下一条事件可能把损坏文件静默替换为只包含新会话的文件。
2. 删除单条会话和清空全部会话没有二次确认，容易误操作。
3. HUD 位置只保存绝对坐标，不保存显示器身份和相对位置；只要窗口与某块屏幕有少量相交就不会纠正，无法可靠支持显示器断开、排列变化和分辨率变化。
4. 真实 Codex 端到端脚本仍断言新会话默认参与 HUD，与已经确认并实现的“新会话默认关闭”规则冲突。
5. 真实端到端脚本仅在发布版二进制不存在时构建，可能实际测试旧程序。
6. Hook 事件处理先刷新全部会话和调度器，再报告本次状态变化，存在调度器先看到新状态、随后又处理同一次变化的时序风险，需要改为可证明的一次性顺序并补测试。

### 中优先级

7. 会话存储错误复用了 Hooks 健康状态，随后 Hooks 刷新可能覆盖存储故障，用户无法判断真实故障来源。
8. Hooks 安装检查只验证命令路径存在，没有精确核对事件、匹配器、类型、超时和同步／异步配置。
9. Hooks 正常状态永久依赖历史成功时间。本项经过讨论后决定：MVP 不增加过期机制。
10. App Server 同步主动请求了 `exec`、全部 `subAgent*` 和 `unknown` 等内部来源，这是同步出大量无关会话的重要原因。

### 低优先级与工程可靠性

11. 红灯与黄灯实际使用同一套动画，未体现“紧急闪烁”和“执行中呼吸”的不同语义。
12. 绿灯完成状态超时回到待机后，内存中的更新时间变化没有写入会话文件。
13. App Server 子进程退出等待没有总时限，异常进程可能导致同步线程长期卡住。
14. Unix Socket 服务端逐连接读取到 EOF；异常客户端若保持连接且不结束发送，会阻塞串行监听队列。
15. 当前 HUD 虽然使用了系统材质，但视觉上接近不透明浅色胶囊，灯位过小、内边距偏大，没有达到参考图中的毛玻璃和醒目状态灯效果。

## 概念说明

### `sessions.json` 是什么

用户询问了 `sessions.json` 的含义。共同理解如下：

- 它位于用户目录下的 `Library/Application Support/Traceflow/sessions.json`。
- 它是 Traceflow 自己维护的本地会话索引，不是 Codex 官方会话文件。
- 它保存会话 ID、项目路径、标题信息、是否参与 HUD、发现与更新时间、排序信息等。
- 它不保存用户对话正文、提示词全文、模型回答、工具输出或实时运行状态。
- 删除或重建它不会删除 Codex 原始对话；正式会话可以通过同步重新发现。

## 问答记录

### 问题 1：`sessions.json` 损坏后如何处理

推荐方案：禁止自动覆盖；HUD 和 Hooks 继续运行，但暂停会话文件写入；设置页明确显示“会话数据损坏”，提供“打开数据目录”和“备份并重建”。重建前保留带时间戳的原文件备份，不自动猜测或修补损坏 JSON。

用户回答：确认。

### 问题 2：删除会话是否二次确认

推荐方案：删除单条会话和清空全部记录都显示二次确认，并明确操作只删除 Traceflow 本地记录，不删除 Codex 原始对话。

用户回答：确认，需要二次提示。

### 问题 3：同步时是否过滤内部会话

推荐方案：只同步用户直接创建的正式会话，即 `cli`、`vscode` 和 `appServer`；排除 `subAgent*`、`exec` 和 `unknown`。

用户回答：确认。

### 问题 4：Hooks 正常状态是否设置七天有效期

推荐方案：最近七天有 Hook 事件显示正常，超过七天显示“需要复检”。

用户回答：本版不增加该机制。设置中已有“安装／修复 Hooks”按钮，用户感觉有问题时可以主动点击。

最终结论：Hooks 一旦验证成功就保持正常，不因为时间流逝自动降级。

### 问题 5：健康状态是否拆分

推荐方案：设置页分别展示 Hooks 配置、本地通信、会话数据三类状态，任何一类故障都不得覆盖另外两类。

用户回答：确认。

### 问题 6：红、黄、绿三盏灯的动画是否区分

推荐方案：红灯使用明显闪烁，黄灯使用柔和呼吸，绿灯常亮；待机不播放动画；系统开启“减少动态效果”时全部静态显示。

用户回答：确认。红灯要更急促，表现紧急和需要处理；黄灯像呼吸灯；绿灯常亮表示完成。点亮状态同时带对应颜色光晕。

### 问题 7：HUD 当前视觉与参考图的差距

用户补充：当前浅色胶囊没有达到目标。整个 HUD 应有半透明毛玻璃效果；右侧三盏圆灯半径太小，没有占满灯区。参考图用于表达胶囊质感、灯位比例和光晕效果。

推荐方案：保持固定宽度，先将灯直径增大到 20 点。

用户补充：内边距也应缩小，或者整体高度稍微降低。

### 问题 8：HUD 紧凑尺寸

推荐方案：HUD 从 `420 × 44` 调整为 `420 × 40` 点；灯直径为 20 点；左侧图标区宽度 40 点；标题左右内边距 8 点；灯间距 8 点；分隔线高度 22 点。

用户回答：确认。

### 问题 9：毛玻璃采用固定颜色还是系统动态材质

推荐方案：使用真正透出 HUD 后方桌面和窗口的 macOS 原生动态毛玻璃，自动适配浅色和深色模式，再叠加轻微高光边框；不把参考图的蓝色作为固定背景。

用户回答：确认。

### 问题 10：是否提供“显示内部会话”高级开关

推荐方案：MVP 不提供，直接过滤内部会话。

用户回答：不提供。

### 问题 11：“备份并重建”后如何恢复会话

推荐方案：备份损坏文件，建立新的空会话文件，然后自动同步正式会话；所有同步回来的会话默认不参与 HUD，由用户自行勾选。

用户回答：确认。

### 问题 12：删除后是否提示未来同步可能重新出现

推荐方案原本包含“以后同步时可能再次出现”的提示。

用户回答：MVP 先不显示这条提示，后续再优化。

最终结论：删除确认只说明“仅删除 Traceflow 本地记录，不删除 Codex 原始对话”，不实现永久忽略列表，也不提示重新同步行为。

### 问题 13：未点亮状态灯的颜色

推荐方案：未点亮的三盏灯仍保留低亮度红、黄、绿色底色，但不产生光晕，使用户始终能识别固定的红、黄、绿顺序。

用户回答：确认。

### 问题 14：HUD 分隔线

推荐方案：保留三个区域的视觉划分，但将两条分隔线改为更淡、更短的半透明细线，避免破坏完整玻璃胶囊的连续感。

用户回答：确认。

### 问题 15：HUD 是否增加灰色底调

用户提出：毛玻璃背景是否可以略带灰色，使三盏灯更明显。

推荐方案：在原生动态毛玻璃上叠加低透明度、自适应中性灰蒙版；浅色模式使用浅灰，深色模式使用深灰。蒙版只压低背景干扰，不能变成不透明灰色胶囊。

用户回答：确认。

### 问题 16：模块和测试范围

推荐方案分为七个模块：会话存储健康与恢复、正式会话过滤与排序、Hooks 精确校验和三类健康状态、删除确认、HUD 视觉、跨显示器位置、调度／进程／Socket／端到端可靠性。

推荐测试范围：存储损坏保护、会话过滤合并、Hooks 校验、轮播状态切换和超时退出编写自动化测试；视觉、确认弹窗和多显示器使用构建检查与人工验收；真实 Codex 端到端脚本强制使用新构建并断言新会话默认关闭。

用户回答：确认。

## 最终共同理解

1. 会话文件损坏时进入只读保护，原文件不得被 Hook、同步、删除、勾选或任何自动保存覆盖。
2. 只读保护期间 Hooks 接收、HUD 展示和内存状态机继续工作；持久化操作必须明确受控，不能伪装为保存成功。
3. 用户可打开数据目录，也可执行“备份并重建”；重建保留原文件备份，创建空索引并自动同步正式会话。
4. 所有重建或同步回来的新会话默认关闭，不参与 HUD。
5. 单条删除与清空全部均需二次确认；文案只说明不会删除 Codex 原始对话。
6. 同步只包含 `cli`、`vscode`、`appServer`，直接排除 `exec`、全部 `subAgent*` 和 `unknown`；MVP 不提供显示内部会话开关。
7. Hooks 配置、本地通信、会话数据分别显示状态，互不覆盖；不增加七天过期或“需要复检”。
8. Hooks 是否安装必须精确校验完整定义，而不是只检查命令路径。
9. HUD 固定为 `420 × 40` 点，图标区 40 点、标题横向内边距 8 点、灯直径 20 点、灯间距 8 点、分隔线高度 22 点。
10. HUD 使用原生动态毛玻璃，并叠加自适应低透明度中性灰、轻微高光描边和阴影。
11. 未点亮灯保持低亮度红、黄、绿底色；点亮后显示对应颜色和光晕。
12. 红灯急促闪烁，黄灯柔和呼吸，绿灯常亮；减少动态效果时取消闪烁、呼吸和缩放，但保留静态状态区分。
13. HUD 保存显示器身份和相对位置；目标显示器不可用时移动到当前主屏幕顶部居中，窗口必须完整位于可见区域。
14. 修复 Hook 状态更新与轮播调度顺序、完成超时持久化、App Server 总超时和 Socket 读取超时。
15. 端到端脚本必须先构建当前源码，不能复用不确定的新旧二进制；真实 Codex 测试断言会话默认关闭。
16. 本次不引入数据库、内部会话开关、Hooks 健康过期、永久忽略列表、HUD 点击动作或自动启动。
