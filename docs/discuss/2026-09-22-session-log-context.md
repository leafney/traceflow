# 会话日志上下文与清除确认讨论纪要

## 原始需求

用户发现 Traceflow 日志仅记录 Hook 事件与状态变化，例如 `event=UserPromptSubmit state=completed->running`，无法从单行判断是哪一个项目、哪一个会话触发。用户要求补足相关上下文信息。同时，设置页“清除日志”按钮当前会立即删除日志，用户要求增加二次确认弹窗。

历史文档只作参考；本纪要中确认的规则优先。

## 逐项问答

1. **日志需要加入哪些可定位信息？**建议在每个已接受 Hook 事件的状态日志中加入项目名、会话 ID、当前标题；不记录完整提示词、对话正文或其他内容。**用户：确认。**
2. **清除日志是否需要二次确认？**建议点击“清除日志”后弹出原生确认框，明确永久删除 Traceflow 所有轮转日志、不会删除会话数据或 Codex 原始对话；只有再次点击危险操作按钮才执行。**用户：确认。**
3. **PRD 的编码对象是低智能模型，应如何表达？**用户要求补充足够细节，避免编码模型误解。**结论：PRD 必须指定日志键名、日志值来源、字段缺失处理、确认框的状态建模、按钮文案、不可改变的现有行为和自动化验收。**

## 最终共同理解

- 对于每一条被状态机接受的 Hook 事件日志，保留原有 `event=` 与 `state=旧->新`，并追加 `project=`、`session_id=`、`title=`。
- `project` 取该会话快照中的项目显示名；`session_id` 为原始会话 ID；`title` 为该会话当前可显示标题。日志不得写入 prompt、会话正文或摘要原文以外的敏感对话内容。
- 日志使用单行、键值对格式；值中出现空白或控制字符时必须转义或引用，保证一条事件永远只占一行。
- 设置页“清除日志”改为先弹出原生二次确认。取消不删除任何文件；确认后调用既有日志清理逻辑，清除当前日志和最多四个轮转副本。不会影响 `sessions.json`、HUD 偏好、Codex 对话、Hooks 配置或应用运行状态。
