# 浮窗布局切换残影补充调查

## 用户复现与澄清

- 原问题：会话标题变化时，固定的默认名称似乎仍留在底层。
- 提问：拖动浮窗时，两段文字是否跟着移动？
- 用户先答只有会话标题移动，随后纠正为两段都跟着整个浮窗移动；轮播时默认名称固定，会话标题滚动。以纠正后的答复为准。
- 新复现：退出并重启，无会话，横向左显示三个灯和默认名称；切横向右后，旧的左侧灯与标题仍以阴影样式留在原位置，新布局显示在上方。
- 新复现不涉及会话标题切换，可以独立调查布局绘制。

## 本次验证事实

- 安装包与dist签名后主程序哈希一致，仅一个应用进程；不是凭猜测认定用户安装了旧版本。
- 读取到设置：横向左、白色标题、背景透明度86%。
- 生产HUD由透明NSPanel、背景材质和NSHostingView组成。
- switchLayout更新布局、图标比例与窗口位置尺寸，复用原NSHostingView；没有显式处理整个旧布局的绘制失效。
- 临时隔离诊断没有发送用户真实Hook、修改用户设置或安装应用。
- 不调用cacheDisplay的左右切换诊断中：同一文字CGDrawingLayer的x从111变7，再变111；三个灯的图层也移到当前布局位置，未观察到两套同时保留的原生图层。
- 默认文字直接位于Hosting主图层，会话文字因compositingGroup位于独立子层。此差异是观察事实，尚未证明是屏幕残留的直接原因。
- 屏幕录制权限不可用，未取得WindowServer合成截图，不能宣称已复现或确认系统缓存缺陷。

## 之前验证为何不足

- HUDLayoutControllerTests只检查尺寸、位置、固定状态和设置，不检查屏幕残影。
- 标题的多布局测试主要逐布局创建新窗口，遗漏同一窗口从旧布局切新布局。
- cacheDisplay重新绘制内容，不能独立验证当前屏幕缓存已被正常清除。
- 把标题字符串与退出动画作为主要修复目标，没有先使用无会话布局切换隔离问题。

## 下一轮修改建议（未实施）

1. 以同一个生产浮窗、无会话、横向左→右→左为首要验收用例；再覆盖竖向互换、横竖互换与有会话切换。
2. 先验证布局变化后的透明承载重绘：旧区域与新区域的并集应失效；需要包含整个HUD内容区，因为灯和标题均有残留。只在布局事件执行，不在每帧或每次会话轮播执行。不得填不透明背景掩盖问题。
3. 如果显式失效仍无法清除实屏残留，下一候选为布局切换时替换内容NSHostingView：保留NSPanel、背景、模型、位置和设置，只移除旧SwiftUI承载及其子层并插入当前布局的新承载。此为条件备选，需先取得前一步失败证据。
4. 会话间滑入、滑出与淡入淡出仍在现有内容承载中运行；不能在每次会话变化重建承载，不能取消动画。
5. 默认与会话绘制路径一致化只在布局修复后仍能独立复现标题残留时处理；不同时叠加多个猜测补丁。
6. 先观察正常屏幕结果再运行cacheDisplay辅助检查，避免验证动作改变待观察状态。实际屏幕无旧文字和旧灯、会话动画仍存在才算验收。

## 当前状态

本轮只调查与提出方案；临时标题结构探针已撤回，临时诊断测试已删除。生产代码没有新增改动，没有安装。根因定位已从会话内容转向布局切换后的原生绘制与屏幕合成，但具体失效环节仍待实屏验证。
