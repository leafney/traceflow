## 1. Problem Statement

用户同时运行多个 Codex CLI 或 Codex 桌面客户端会话时，需要不断切回终端或客户端才能判断每个会话是在执行、等待权限还是已经完成。多会话并行时，这种检查会打断当前工作，并容易遗漏需要人工处理的权限请求。

用户需要一个轻量、始终可见但不抢键盘焦点的 macOS HUD，在不改变 Codex 正常行为的前提下，集中展示各会话状态，并公平轮播所有被用户选中的会话。

## 2. Solution

构建名为 Traceflow 的 macOS 菜单栏应用。应用由以下部分组成：

- 一个常驻 macOS App，负责菜单栏、设置窗口、悬浮 HUD、状态聚合、轮播、存储和日志。
- 一个短生命周期命令行转发器 `traceflow-notify`，由 Codex Hooks 启动，读取 stdin JSON，并通过本地 Unix Domain Socket 转发给 App。
- 一个独立纯逻辑核心模块，封装事件解析、状态机、标题生成和轮播调度，便于单元测试。
- 用户级 `~/.codex/hooks.json` 中的一组 Traceflow Hook 条目，监听最小必要事件集合。

HUD 固定为 `420 × 44 pt`，从左到右显示 Codex 图标、当前会话标题以及红、黄、绿三个固定灯位。它支持拖动、多显示器、位置保存、所有空间和全屏应用，不接收键盘焦点。用户通过菜单栏打开设置，管理 HUD、Hooks 和参与轮播的会话。

## 3. Goals

1. 尽快验证 Codex CLI 与 Codex 桌面客户端能否共用用户级 Hooks 完成状态上报。
2. 完成 `Hooks → 转发器 → Unix Socket → 状态机 → 轮播 → HUD` 的真实闭环。
3. 准确表达执行中、等待权限、已完成和待机四种语义。
4. 在多个会话并发变化时，既快速提示红灯事件，又保证全部已勾选会话最终可见。
5. 不改变 Codex 的权限决定、工具输入、提示词或执行流程。
6. 将隐私数据控制在最低范围，不落盘完整提示词、对话摘要、工具输入或工具输出。

## 4. User Stories

1. 作为同时运行多个 Codex 会话的用户，我希望在一个悬浮 HUD 中看到当前会话状态，从而无需反复切换窗口。
2. 作为 Codex CLI 用户，我希望 Traceflow 能通过用户级 Hooks 接收事件，从而跟踪终端中的任务。
3. 作为 Codex 桌面客户端用户，我希望同一套 Hooks 也能上报事件，从而不需要另一套适配配置。
4. 作为用户，我希望黄灯表示任务正在执行，从而快速知道任务尚未结束。
5. 作为用户，我希望红灯表示 Codex 正在等待权限审批，从而及时介入。
6. 作为用户，我希望绿灯表示一轮任务已经完成，从而知道可以查看结果。
7. 作为用户，我希望待机会话三个灯全部熄灭，从而区分“无活动”和“任务完成”。
8. 作为用户，我希望点亮的灯带有柔和光晕，从而更容易识别当前状态。
9. 作为用户，我希望红灯缓慢闪烁，从而突出需要人工处理的状态。
10. 作为用户，我希望黄灯使用呼吸效果，从而表达持续执行。
11. 作为用户，我希望绿灯稳定常亮，从而避免完成状态产生不必要干扰。
12. 作为启用“减少动态效果”的用户，我希望 Traceflow 停止闪烁和呼吸并使用温和过渡，从而符合系统辅助功能偏好。
13. 作为用户，我希望 HUD 显示项目名和对话摘要，从而辨认当前会话。
14. 作为用户，我希望无法获得摘要时仍显示项目目录名，从而不会出现空标题。
15. 作为用户，我希望标题保持单行且超长时尾部省略，从而保持 HUD 尺寸稳定。
16. 作为用户，我希望同一会话的标题不会随每轮输入不断变化，从而保持识别稳定。
17. 作为用户，我希望多个会话公平轮播，从而不会永久看不到某个低优先级状态。
18. 作为用户，我希望新权限请求立即抢占普通状态，从而尽快看到红灯。
19. 作为用户，我希望正在展示的红灯至少完整显示一个轮播周期，从而有时间识别会话。
20. 作为用户，我希望所有会话待机时仍继续轮播，从而确认每个已管理会话都处于待机。
21. 作为用户，我希望只有一个会话时不播放无意义切换动画，从而减少视觉噪音。
22. 作为用户，我希望在设置页通过复选框决定哪些会话参与 HUD，从而控制轮播内容。
23. 作为用户，我希望取消当前会话勾选后立即显示下一个会话，从而使设置立刻生效。
24. 作为用户，我希望删除 Traceflow 本地会话记录而不删除 Codex 对话，从而安全整理列表。
25. 作为用户，我希望被删除的会话再次产生事件时重新出现，从而不会永久丢失跟踪能力。
26. 作为用户，我希望退出并重启 Traceflow 后保留会话选择和 HUD 位置，从而减少重复设置。
27. 作为用户，我希望重启后过期的红黄绿状态不被恢复，从而避免错误提示。
28. 作为用户，我希望首次启动时 HUD 位于主屏顶部居中，从而立即可见。
29. 作为用户，我希望拖动 HUD 后自动保存位置，从而按自己的工作区布局放置。
30. 作为多显示器用户，我希望能把唯一一个 HUD 拖到任意显示器，从而选择合适的观看位置。
31. 作为多显示器用户，我希望原显示器断开后 HUD 自动回到主屏可见区域，从而不会丢失窗口。
32. 作为正在输入的用户，我希望 HUD 永远不抢键盘焦点，从而不打断当前操作。
33. 作为使用多个桌面空间或全屏应用的用户，我希望 HUD 保持可见，从而持续获得状态信息。
34. 作为用户，我希望点击 HUD 不触发动作，从而避免 MVP 中意外展开或切换。
35. 作为用户，我希望菜单栏图标始终稳定且不闪烁，从而避免重复状态提示。
36. 作为用户，我希望从菜单栏显示或隐藏 HUD，从而按需减少遮挡。
37. 作为用户，我希望从菜单栏打开设置或退出应用，从而完成基本控制。
38. 作为用户，我希望首次安装 Hooks 必须由我主动点击，从而避免应用未经确认修改配置。
39. 作为已有自定义 Hooks 的用户，我希望 Traceflow 合并配置而不是覆盖文件，从而保留现有自动化。
40. 作为用户，我希望修改 Hooks 前自动备份，从而能在故障时恢复。
41. 作为用户，我希望可以修复或移除 Traceflow Hooks，且只影响 Traceflow 自己的条目。
42. 作为用户，我希望设置页显示 Hooks 的可验证状态，从而判断尚未安装、等待验证、正常或异常。
43. 作为用户，我希望安装后得到 `/hooks` 信任提示，从而完成 Codex 官方安全审核。
44. 作为 Codex 用户，我希望 Traceflow 未运行时转发器快速退出，从而不拖慢 Codex。
45. 作为隐私敏感用户，我希望完整提示词、摘要、工具输入和工具输出不进入日志或持久化存储。
46. 作为排障用户，我希望日志有明确大小上限，从而不会无限占用磁盘。
47. 作为排障用户，我希望能从设置页打开日志目录并清除日志，从而方便检查和维护。
48. 作为本机开发者，我希望核心状态与调度逻辑有单元测试，从而能快速验证方案是否正确。

## 5. Product Behavior Specification

### 5.1 产品与进程命名

- 产品、App 和界面名称统一为 `Traceflow`。
- 命令行转发器名称为 `traceflow-notify`。
- 历史名称 `Codex HUD` 不得用于新代码、菜单、设置标题或日志前缀。
- MVP 统一将 Agent 类型标记为 `codex`，CLI 与桌面端不区分图标。

### 5.2 菜单栏

菜单栏使用固定单色 Traceflow 图标，不根据会话状态变色、闪烁或显示徽标。菜单至少包含：

1. `显示 HUD` 或 `隐藏 HUD`，根据当前状态动态显示其中一个。
2. `设置…`，打开普通可聚焦的设置窗口。
3. 分隔线。
4. `退出 Traceflow`。

退出只终止 App，不删除 Hooks、转发器、设置、日志或会话记录。

### 5.3 HUD 布局

- 固定尺寸：宽 `420 pt`，高 `44 pt`。
- 外框：跟随系统深浅色的半透明毛玻璃材质，细边框，轻阴影，圆角接近胶囊形态。
- 左侧图标区：宽约 `44 pt`，居中显示 Codex 图标；图标不可用时显示 Traceflow 默认图标。
- 中间标题区：占剩余主要宽度，单行，尾部省略，不换行，不撑大 HUD。
- 右侧状态区：固定显示三个直径约 `12 pt` 的灯，间距约 `10 pt`，从左到右严格为红、黄、绿。
- 标题区与状态区之间显示细分隔线。
- 点击 HUD 本体不执行命令、不展开列表、不打开设置。
- HUD 可通过背景拖动，但不得因此成为 key window 或抢占键盘焦点。

### 5.4 HUD 显示与位置

- 首次启动默认显示。
- 用户隐藏后保存该选择，后续启动沿用。
- 如果没有任何已勾选会话，HUD 仍可显示：标题为 `Traceflow`，三灯全灭。
- 首次位置：当前主屏幕顶部水平居中，位于可见工作区内，并与菜单栏底部保留约 `12 pt` 距离。
- 全局只创建一个 HUD，不为每个显示器复制。
- 保存 HUD 所在显示器标识和相对该显示器可见工作区的位置。
- App 重启时优先恢复原显示器和位置。
- 显示器断开、分辨率改变或保存位置不可见时，将 HUD 限制到当前可见区域；原显示器不存在时移到主屏顶部居中。
- HUD 加入所有桌面空间，并允许显示在全屏应用之上；层级高于普通窗口，但不得试图覆盖系统菜单、系统通知或授权弹窗。
- HUD 使用非激活面板，必须满足 `canBecomeKey == false` 和 `canBecomeMain == false` 的等价行为。

### 5.5 标题生成

标题组件只能使用以下信息：

- `projectName`：从 Hook 的 `cwd` 标准化后取最后一个非空路径组件。
- `conversationSummary`：从当前会话第一次可用的 `UserPromptSubmit.prompt` 生成。

摘要生成规则：

1. 只在该会话尚无摘要时处理；一旦得到首个有效摘要，后续用户输入不改变标题。
2. 将换行统一后，选择第一个非空文本行。
3. 去除行首常见 Markdown 标记，例如标题符号、列表符号和引用符号。
4. 折叠连续空白为一个空格，并去除首尾空白。
5. 清理后为空则视为无摘要，允许后续输入再次尝试。
6. 最多保留 30 个用户可见字符；超出时截断。不得调用 AI、网络服务或读取 transcript 来生成摘要。
7. 摘要只存在内存，不写入会话 JSON、`UserDefaults`、日志或健康文件。

最终标题按以下顺序自动降级：

1. 同时有项目名和摘要：`项目名 · 对话摘要`。
2. 只有摘要：`对话摘要`。
3. 只有项目名：`项目名`。
4. 两者都没有：`未知会话`。

App 重启后摘要丢失，因此先显示项目名；收到该会话后续输入时可重新生成新的“首次有效摘要”。这是 MVP 的已知折中。

### 5.6 状态定义与灯效

运行时状态只有四种：

| 状态 | HUD | 语义 | 动效 |
|---|---|---|---|
| `idle` | 三灯全灭 | 会话存在但当前无活动 | 无 |
| `running` | 黄灯点亮 | 用户已提交任务或工具执行后仍在任务中 | 缓慢呼吸 + 黄色柔光 |
| `attention` | 红灯点亮 | Codex 正在等待权限审批 | 缓慢闪烁 + 红色柔光 |
| `completed` | 绿灯点亮 | 一轮任务已经停止并可查看 | 常亮 + 绿色柔光 |

未激活灯使用低透明度占位，不显示光晕。点亮灯的光晕不能改变布局尺寸或影响标题可读性。

光晕强度设置为三档：

- 低：较小半径、较低透明度。
- 中：默认，清晰但不刺眼。
- 高：更大半径和更高透明度，但不得溢出到标题区域造成明显遮挡。

系统启用“减少动态效果”时：

- 禁止红灯闪烁和黄灯呼吸。
- 保留静态点亮和静态光晕。
- 会话切换由滑动改为短淡入淡出。

### 5.7 Hook 事件到状态的映射

每个会话以 `session_id` 为唯一键。必须按下表处理：

| Hook 事件 | 条件 | 新状态 | 其他动作 |
|---|---|---|---|
| `SessionStart` | `source` 为 `startup`、`resume` 或 `clear` | `idle` | 创建或更新会话、项目路径和项目名 |
| `SessionStart` | `source` 为 `compact` | 不变 | 忽略，不更新时间、不入队 |
| `UserPromptSubmit` | 有效事件 | `running` | 尚无摘要时尝试生成摘要 |
| `PermissionRequest` | 任意工具审批 | `attention` | 不返回 allow/deny，不改变审批流程 |
| `PostToolUse` | 任意工具完成 | `running` | 解除之前的红灯语义 |
| `Stop` | 有效事件 | `completed` | 记录进入完成状态的挂钟时间 |
| `Interrupt` | 有效事件 | `idle` | 清除完成状态计时 |
| `SessionEnd` | 有效事件 | `idle` | 保留会话，不自动删除 |
| 内部超时 | `completed` 连续满 10 分钟且无更新 | `idle` | 作为状态变化进入普通事件队列 |

补充规则：

- 同一状态的重复事件不是状态变化：更新最后活动时间及允许更新的元数据，但不得重复抢占或重复入队。
- `PostToolUse` 只在事件到达后将状态改为 `running`；MVP 不尝试推断用户究竟批准或拒绝了请求。
- 绿转待机基于挂钟时间差，而不是假设定时器准时触发。App 唤醒后必须重新检查所有完成状态。
- `SessionEnd` 不删除会话；会话只有用户在设置页主动删除时才从本地列表消失。
- 运行状态永远不持久化。App 每次启动后，所有已保存会话均从 `idle` 开始。

## 6. Carousel Scheduling Contract

### 6.1 基本概念

- `selectedSessions`：设置页中已勾选、参与 HUD 的会话集合。
- `currentSession`：HUD 当前显示的会话。
- `displayDuration`：用户设置的每会话展示时间，可选 3、5、10 秒，默认 5 秒。
- `redQueue`：等待展示的红灯会话 FIFO 队列。
- `eventQueue`：等待展示的黄、绿、待机会话 FIFO 队列。
- `rotationOrder`：所有已勾选会话的稳定轮播顺序。MVP 使用首次发现顺序；删除后重新发现的会话排到末尾。

### 6.2 去重规则

- 每个队列中，同一个 `session_id` 最多存在一次。
- 同一会话在等待时再次发生状态变化，更新其最新状态快照，但保留原队列位置。
- 如果新状态变为红灯，应从普通队列移除并加入红灯队列尾部。
- 如果会话被取消勾选或删除，应立即从两个队列移除。

### 6.3 新状态变化的处理

按以下顺序执行，不得自行改成“红 > 黄 > 绿 > 待机”的长期分组轮播：

1. 如果没有已勾选会话，显示 Traceflow 占位。
2. 如果只有一个已勾选会话，立即更新该会话显示，不播放切换动画，也不维护无意义队列。
3. 如果发生变化的是当前会话：立即更新灯和标题；若变为红灯，则从此刻重新计算一个完整展示周期；非红状态不额外复制入队。
4. 如果非当前会话变为红灯，且当前会话不是红灯：立即打断当前展示，切换到该红灯会话，并从切换完成后开始计算完整展示周期。被打断会话回到正常轮播，不放入事件队列补时。
5. 如果当前会话已经是红灯：任何其他新红灯不得打断它，而是按到达顺序加入 `redQueue`。
6. 如果非当前会话变为黄、绿或待机：加入或更新 `eventQueue`，等待当前完整展示周期结束。
7. 同一状态重复事件不触发上述抢占或入队逻辑。

### 6.4 一个展示周期结束后的选择顺序

当前会话完成一个完整展示周期后，严格按以下顺序选下一个：

1. 从 `redQueue` 队首取第一个仍存在且已勾选的会话。
2. 若红灯队列为空，从 `eventQueue` 队首取第一个仍存在且已勾选的会话。
3. 若两个队列都为空，按 `rotationOrder` 选择当前会话之后的下一个已勾选会话，并循环回开头。
4. 若候选与当前会话相同且没有其他会话，不触发动画。

每个从队列取出的会话都获得完整展示周期。多个红灯按到达顺序逐个完整展示。这个机制提供红灯即时性，但不会让长期红灯永久屏蔽其他会话。

### 6.5 会话切换动画

- 正常模式：旧内容向上滑出，新内容从下方进入，总时长约 250ms。
- HUD 外框和位置保持不动。
- 图标、标题和三灯作为一个内容组同步切换。
- 展示计时从切换动画完成时开始，保证用户获得完整的 3、5 或 10 秒可读时间。
- 减少动态效果模式：使用短淡入淡出，不做位移动画。

### 6.6 特殊场景

- 所有会话都是 `idle`：仍按稳定顺序轮播，每项三灯全灭。
- 当前会话被取消勾选或删除：立即清理队列并选择下一项；没有选中项则显示 Traceflow 占位。
- 新发现会话：默认勾选并加入轮播顺序末尾；其首次状态变化遵循正常抢占规则。
- App 从睡眠唤醒：先做完成超时检查，再将产生的状态变化交给调度器。

## 7. Hooks Integration Contract

### 7.1 开发前置 Gate

在搭建完整 UI 前，必须先用最小 PoC 在真实环境验证：

1. Codex CLI 能读取用户级 `~/.codex/hooks.json` 并触发所需事件。
2. Codex 桌面客户端能读取同一配置并触发所需事件。
3. 两端 payload 都能取得稳定的 `session_id`、`cwd`、`hook_event_name`；回合事件能取得 `turn_id`。
4. 实测确认各事件时机，尤其是 `Stop`、`PermissionRequest`、`PostToolUse`、`Interrupt` 和 `SessionEnd`。
5. 同一项目的多个会话具有不同 `session_id`。

如果桌面端不能产生所需事件，必须停止后续实现并请求用户决定替代方式；不得自行交付 CLI-only 版本并声称完成双端 MVP。

PoC 结果应形成独立开发记录，后续实现以实测行为优先，但任何导致需求语义变化的调整仍需用户确认。

### 7.2 监听事件

用户级配置只添加以下事件：

- `SessionStart`，matcher 只匹配 `startup|resume|clear`。
- `UserPromptSubmit`。
- `PermissionRequest`，不限制工具类型。
- `PostToolUse`，不限制工具类型。
- `Stop`。
- `Interrupt`。
- `SessionEnd`。

不得添加 `PreToolUse`、`PreCompact`、`PostCompact` 或其他无关事件。

除 `SessionEnd` 外，Traceflow Hook 可设为后台异步执行，以避免阻塞 Codex。`SessionEnd` 按官方行为同步执行，配置中不要虚假声明依赖异步行为。所有命令使用短超时，目标值 3 秒；转发器自身应远快于此值完成。

Hook 只旁路观察：

- 不允许审批或拒绝 `PermissionRequest`。
- 不允许修改工具输入、权限或模型上下文。
- 不允许阻止用户提示、继续 Stop 或中断 turn。
- 不得输出会影响 Codex 的文本。
- 对要求 JSON stdout 的事件输出空 JSON 对象 `{}`；其他事件也可统一输出 `{}`，但不得包含控制字段。

### 7.3 安装、修复与移除

首次启动不得自动修改 `~/.codex/hooks.json`。只有用户在设置页点击“安装/修复 Hooks”时才执行。

安装流程必须是：

1. 确认转发器已复制到固定位置并具有可执行权限。
2. 如果 `hooks.json` 存在，先读取原始字节并解析为 JSON。
3. JSON 无效时停止，不覆盖、不重建，设置页显示明确错误。
4. JSON 有效时创建带时间戳的原文件备份。
5. 保留所有未知顶层字段、其他事件、matcher 组和 handler。
6. 使用固定转发器命令路径识别 Traceflow 自己的 command handler。
7. 对每个目标事件删除旧 Traceflow handler，再插入唯一的新 handler，避免重复安装。
8. 若移除 handler 后某个 Traceflow 专用 matcher 组为空，可删除空组；不得删除含用户其他 handler 的组。
9. 将新 JSON 写到同目录临时文件，重新解析验证成功后原子替换正式文件。
10. 安装完成后显示提示：在 Codex 中执行 `/hooks`，审核并信任新定义，然后发送一条消息进行验证。

“修复 Hooks”重复执行同一流程，结果必须幂等：连续执行多次，每个事件仍只有一个 Traceflow handler。

“移除 Hooks”必须：

1. 备份并解析现有文件。
2. 只删除命令路径匹配 Traceflow 固定转发器的 handler。
3. 保留全部其他配置。
4. 验证并原子写回。
5. 成功移除配置后，可删除已安装的转发器；不得删除 Traceflow 会话、偏好或日志。

### 7.4 转发器固定位置与职责

固定安装位置：

`~/Library/Application Support/Traceflow/bin/traceflow-notify`

路径必须长期稳定。不得让 Hook 指向 Xcode DerivedData、仓库构建目录或可能随版本变化的 App bundle 路径。

转发器只能执行：

1. 从 stdin 完整读取单个 Hook JSON 对象，并限制最大输入大小。
2. 做最小 JSON 验证，读取公共字段但不解释业务状态。
3. 尽早生成宿主级单调时间戳和唯一事件 ID。
4. 包装成版本化信封。
5. 连接本地 Unix Domain Socket，发送一条消息，关闭连接并退出。
6. App 未运行、Socket 不存在或连接失败时快速退出，不自动启动 App、不重试、不排队。
7. 对预期的“App 未运行”场景保持安静，不向 Codex 展示错误。
8. 不写完整 payload 到磁盘。

建议单次执行目标：正常本地转发在数十毫秒级完成；连接失败应在 200ms 左右主动结束，硬上限不得接近 Hook 的 3 秒超时。

### 7.5 IPC 信封

转发器发送的顶层信封必须包含：

| 字段 | 类型 | 含义 |
|---|---|---|
| `schema_version` | 整数 | MVP 固定为 1 |
| `event_id` | 字符串 | 每次转发唯一 UUID |
| `captured_uptime_ns` | 无符号整数 | 转发器读取事件后立即取得的单调时间 |
| `forwarded_at` | ISO 8601 字符串 | 用于诊断的挂钟时间 |
| `payload` | JSON 对象 | Codex 原始 Hook payload |

不在信封中复制 prompt 或工具数据到其他字段。

### 7.6 Unix Domain Socket

- Socket 固定放在 Traceflow 应用支持目录中，文件名 `traceflow.sock`。
- 应用支持目录权限应限制为当前用户。
- App 启动时清理只属于该固定路径的陈旧 Socket 文件，再绑定监听。
- 一次连接只发送一个信封；以连接 EOF 作为消息边界，不拼接多个 JSON。
- 对单条消息设置合理上限，建议 1 MiB；超过上限立即丢弃并记无敏感信息的错误日志。
- 多个并发连接必须串行送入状态存储，避免并发修改 UI 状态。
- JSON 解析失败不能导致监听器退出。
- MVP 不宣称 Socket 加密。本机用户目录权限和 Socket 权限是访问边界。

### 7.7 乱序处理

每个会话保存 `lastAppliedUptimeNs`：

- 新事件时间戳小于已应用时间戳：丢弃，不改变状态、标题、队列或更新时间，只记录脱敏诊断信息。
- 新事件时间戳大于已应用时间戳：正常处理并更新记录。
- 时间戳相等：以 App 实际接收顺序处理，并用 `event_id` 去重。
- 已处理的 `event_id` 应有小型有界缓存，防止同一消息重复应用；缓存无需持久化。

不读取 Codex transcript，不根据文件时间排序，不实现跨机器时间同步。

## 8. Settings Window

设置窗口是普通可聚焦窗口，至少包含三个分区。

### 8.1 常规

- `显示 HUD`：开关，和菜单栏命令同步。
- `轮播间隔`：3 秒、5 秒、10 秒，默认 5 秒。
- `光晕强度`：低、中、高，默认中。
- `恢复 HUD 默认位置`：立即将 HUD 放回当前主屏顶部居中并保存。

不得提供开机自动启动、主题、颜色、字体、HUD 尺寸或自定义动画设置。

### 8.2 Codex Hooks 状态卡片

状态只在设置页展示：

| 状态 | 颜色 | 判定 |
|---|---|---|
| 未安装 | 灰 | 配置中缺少完整 Traceflow handler 或转发器缺失 |
| 待验证 | 黄 | 配置和转发器存在，但从未收到真实 Hook 事件 |
| 正常 | 绿 | 已成功收到至少一个真实 Hook 事件；显示最近事件时间 |
| 异常 | 红 | 配置解析失败、转发器不可执行、Socket 自检失败或最近转发健康信息报告错误 |

卡片操作：

- `安装/修复 Hooks`
- `移除 Hooks`
- 必要时显示“请在 Codex 中执行 `/hooks` 并发送一条消息”的说明
- 显示最近成功事件时间或短错误原因；不得显示 prompt、完整项目路径或工具输入

不得把“配置存在”等同于“已经信任”。Codex 的信任状态只能通过实际事件成功到达间接验证，MVP 不伪造官方信任查询。

### 8.3 会话

每行至少显示：

- `参与 HUD` 复选框。
- 当前可用标题；重启后通常只有项目名。
- 当前运行状态。
- 项目路径，允许在设置页显示。
- 短会话标识：由 `session_id` 派生的短文本。
- 最后更新时间。
- `删除记录` 操作。

列表另提供 `清空全部记录`。执行删除前应使用清晰确认，说明只删除 Traceflow 本地记录，不删除 Codex 对话。

规则：

- 新发现会话默认勾选。
- 取消勾选只停止 HUD 展示，不删除记录，也不停止接收状态更新。
- 删除或清空只影响 Traceflow；同一会话未来再次产生 Hook 时重新加入并默认勾选。
- MVP 不做搜索、自定义排序、分组、重命名、批量选择或会话详情页。

## 9. Persistence Model

### 9.1 UserDefaults

保存以下偏好：

- HUD 是否显示。
- 轮播间隔。
- 光晕强度。
- HUD 显示器标识。
- HUD 相对可见工作区的位置。
- 设置 schema 版本。

偏好缺失或无效时使用本文默认值，不得导致 App 无法启动。

### 9.2 会话 JSON

会话列表存放在 Traceflow 应用支持目录的 JSON 文件中，顶层包含 schema 版本和会话数组。每条记录至少包含：

| 字段 | 类型 | 是否持久化 | 说明 |
|---|---|---|---|
| `sessionId` | 字符串 | 是 | Codex 会话唯一键 |
| `agentType` | 字符串 | 是 | MVP 固定 `codex` |
| `projectPath` | 字符串或空 | 是 | Hook 的 cwd 标准化结果 |
| `projectName` | 字符串或空 | 是 | 路径最后一级名称 |
| `isIncludedInHUD` | 布尔 | 是 | 默认 true |
| `discoveredAt` | 日期 | 是 | 首次发现时间 |
| `lastUpdatedAt` | 日期 | 是 | 最后有效事件时间 |
| `rotationIndex` | 整数 | 是 | 稳定首次发现顺序，或用数组顺序等价表达 |
| `conversationSummary` | 字符串 | 否 | 只能在内存 |
| `runtimeState` | 枚举 | 否 | 启动时固定恢复 idle |
| `lastAppliedUptimeNs` | 整数 | 否 | 仅本次 App 生命周期有效 |

写入要求：

1. 所有修改通过单一串行存储入口。
2. 先写同目录临时文件。
3. 验证临时 JSON 可读取后原子替换。
4. 文件损坏时不得静默覆盖；记录错误并在设置页显示，尽量保持 App 其他功能可运行。
5. MVP 不使用数据库。第二版可评估 SQLite，但不得提前引入数据库抽象导致 MVP 复杂化。

## 10. Logging and Privacy

### 10.1 日志位置与轮转

日志目录为 `~/Library/Logs/Traceflow/`。

- 活跃日志最大 10 MiB。
- 总共最多 5 个文件，包含活跃文件。
- 达到上限后按大小轮转，重命名旧文件并删除最老文件。
- 不按日期或保留天数删除。
- 预计总上限约 50 MiB。
- 轮转和写入必须串行，避免并发破坏文件。

### 10.2 可以记录

- 时间戳。
- Hook 事件类型。
- `session_id` 的不可逆短哈希，不记录原值。
- 旧状态与新状态。
- 丢弃乱序事件、JSON 解析失败、Socket 错误、配置安装错误等错误代码。
- App 生命周期、监听器启动停止、显示器位置修正等诊断事件。

### 10.3 禁止记录

- 完整 prompt。
- 对话摘要。
- `last_assistant_message`。
- 工具输入、工具输出、命令文本或权限原因。
- 完整项目路径。
- transcript 内容或路径。
- 原始 Hook JSON。

设置页提供“打开日志目录”和“清除日志”。清除日志不得影响设置、会话或 Hooks。

## 11. Module Design

实现以下深模块，每个模块通过小而稳定的接口隐藏内部复杂度。

### 11.1 TraceflowCore

纯 Swift 逻辑，不依赖 AppKit 窗口。职责：

- 定义 IPC 信封、Hook 事件、会话记录和运行状态。
- 严格解析并验证只需要的字段；保留未知字段兼容未来版本。
- 标题摘要生成与降级。
- 单会话状态机和乱序过滤。
- 完成状态 10 分钟转待机的时间判断，时间源可注入。
- 轮播调度器、红灯队列、普通事件队列和公平轮播。
- 对外返回明确的状态变化结果，不直接操作 UI。

建议核心接口语义：输入事件和当前时间，输出“是否接受、旧状态、新状态、标题是否变化、是否需要调度”。调度器输入会话变化和时间推进，输出当前应展示的 `session_id` 及切换原因。

### 11.2 Traceflow App

职责：

- App 生命周期和菜单栏。
- `NSPanel` HUD 宿主与 SwiftUI 内容。
- 设置窗口。
- Socket 服务、事件串行化和 Core 调用。
- `UserDefaults`、会话 JSON、日志与健康状态。
- 显示器变化、系统睡眠唤醒和减少动态效果监听。
- Hooks 安装器和转发器安装。

UI 不得自行复制状态机判断；所有状态变化和下一会话选择由 Core 决定。

### 11.3 traceflow-notify

独立 Swift 可执行目标。职责仅限 stdin、信封、Socket 和安静退出。不得链接 SwiftUI，不得包含会话状态、标题或轮播逻辑。

### 11.4 TraceflowCoreTests

只依赖 Core。通过可控时钟和事件工厂测试外部行为，不启动窗口、不读写真实用户 Hooks。

## 12. Implementation Plan

编码模型必须按阶段顺序实施。每个阶段完成后，根据用户工作流要求停下等待确认，不得一次性越过所有重大文件变更。

### 阶段 0：真实 Hooks PoC

1. 编写临时只记录字段名和脱敏值的接收工具。
2. 验证 CLI 七类事件及 payload。
3. 验证桌面端七类事件及 payload。
4. 验证多会话 `session_id` 隔离。
5. 记录与官方文档或本 PRD 假设的差异。
6. 双端通过后才继续；桌面端失败则停止并请用户决策。

验收：形成可重复的实测记录，证明双端至少能完成黄、红、绿、待机所需事件闭环。

### 阶段 1：工程骨架与核心数据模型

1. 创建 macOS 14+ App、Core library、转发器和测试目标。
2. 定义版本化事件信封、Hook 事件和会话模型。
3. 实现标题生成、状态机、10 分钟超时和乱序过滤。
4. 实现轮播调度器及全部核心测试。

验收：无需 UI，核心测试全部通过；给定事件序列可输出正确状态与当前会话。

### 阶段 2：IPC 与真实转发器

1. 实现转发器 stdin 读取、大小限制、信封和快速失败。
2. 实现 App Socket 监听、陈旧 Socket 清理、单连接单消息协议。
3. 将收到的真实事件送入 Core。
4. 实现无敏感信息日志和转发健康状态。

验收：多个并发真实 Hook 可更新内存会话；App 未运行时 Codex 无明显延迟和错误噪音。

### 阶段 3：HUD 与菜单栏

1. 实现菜单栏菜单和单色图标。
2. 实现不抢焦点的单实例 `NSPanel`。
3. 实现固定布局、标题、省略、三灯和光晕。
4. 实现切换动画、减少动态效果和轮播计时。
5. 实现拖动、多显示器位置保存及可见范围修正。

验收：HUD 在普通窗口、不同空间、全屏和多显示器场景下可见且不抢键盘焦点；状态与轮播符合 Core 输出。

### 阶段 4：设置、持久化与日志

1. 实现常规设置。
2. 实现会话复选框、删除和清空。
3. 实现会话 JSON 原子保存和重启恢复待机。
4. 实现 Hooks 状态卡片。
5. 实现 10 MiB × 5 文件日志轮转、打开目录和清除日志。

验收：重启后偏好、位置、项目记录和勾选恢复；摘要和运行状态不恢复；删除不影响 Codex 数据。

### 阶段 5：Hooks 安装器与本机闭环

1. 将转发器安装到固定路径。
2. 实现安全备份、解析、合并、幂等修复和精确移除。
3. 完成 `/hooks` 信任提示。
4. 使用 CLI 和桌面端进行端到端验收。
5. 验证退出 App、未运行转发、睡眠唤醒、显示器拔插和坏配置错误路径。

验收：满足本 PRD 第 15 节全部标准。

## 13. Testing Decisions

### 13.1 测试原则

- 测试公开行为和状态输出，不断言私有数组、计时器类型或 SwiftUI 视图层级。
- 时间相关测试使用注入的虚拟时钟，禁止真实等待 3 秒、5 秒或 10 分钟。
- 事件测试使用最小 JSON fixture，不包含真实 prompt、路径或密钥。
- 文件测试使用临时目录，不读写开发者真实 `~/.codex/hooks.json`。
- 现有仓库没有可复用测试先例，因此 Core 测试作为首个基准。

### 13.2 必测模块

#### 标题生成

- 项目名 + 首个有效摘要组合。
- 仅摘要、仅项目名、全缺失的降级。
- 空行、Markdown 标记、多空格和 30 字截断。
- 后续 prompt 不覆盖首个有效摘要。
- 首次输入无有效摘要时，后续输入可以补全。

#### 状态机

- 七类 Hook 的映射。
- compact 完全忽略。
- 同状态重复事件不产生状态跳变。
- `PostToolUse` 将红灯改为黄灯。
- `Stop` 进入绿色，9 分 59 秒不待机，10 分钟时转待机。
- 睡眠式大跨度时间推进后正确转待机。
- `SessionEnd` 变待机但不删除会话。
- 旧时间戳事件丢弃，相同 `event_id` 不重复应用。

#### 轮播调度器

- 单会话不切换。
- 所有待机会话仍公平轮播。
- 非红变化进入 FIFO，当前项展示完整周期。
- 非红展示期间新红灯立即抢占。
- 当前红灯不被另一个红灯中断。
- 多个红灯按 FIFO 且每个完整展示。
- 同一会话多次排队只保留一个位置和最新状态。
- 取消勾选、删除和清空能清理队列。
- 两个优先队列为空时按稳定顺序循环。
- 被红灯打断的普通会话回到常规轮播，不获得隐式补时。

#### 存储

- JSON 写入后可读回。
- 重启恢复时全部运行状态为待机且无摘要。
- 无效偏好回落默认值。
- 临时写入失败不破坏原文件。

#### Hooks 合并器

- 空文件不存在时创建正确结构。
- 保留未知顶层字段和用户已有 handler。
- 连续安装两次不重复 Traceflow handler。
- 修复只更新 Traceflow handler。
- 移除只删除固定命令路径匹配项。
- 非法 JSON 拒绝修改。
- 原子替换前验证失败时保留原文件。

#### 日志轮转

- 文件达到 10 MiB 后轮转。
- 最多保留 5 个文件。
- 不按日期删除。
- 日志格式不包含 prompt、摘要、完整路径和工具内容。

### 13.3 手动验收

- 菜单栏、HUD、设置窗口实际视觉与交互。
- HUD 不抢终端、编辑器或 Codex 输入焦点。
- 所有空间、全屏应用与显示器拔插。
- 系统深浅色和减少动态效果。
- CLI 与桌面端真实 Hooks。
- `/hooks` 信任前后状态卡片变化。
- App 未运行时转发器快速退出。

## 14. Error Handling

- Hook 配置 JSON 无效：不修改文件，显示异常状态和可理解错误。
- 转发器缺失或不可执行：状态为未安装或异常，引导修复。
- Socket 绑定失败：HUD 仍可显示历史会话，但 Hooks 状态为异常；日志记录错误码。
- 单条 Hook JSON 无效：丢弃该条，监听服务继续运行。
- 未知 Hook 事件：忽略并记低级别诊断，不崩溃。
- 缺少 `session_id`：丢弃，因为无法安全归属会话。
- 缺少 `cwd`：允许创建会话，项目名为空，标题按降级规则处理。
- 会话 JSON 损坏：不得静默覆盖；保留文件并提示异常，允许用户后续处理。
- HUD 保存位置无效：回到主屏顶部居中。
- App 未运行：转发器安静快速退出，此情况不是 Codex 错误。

## 15. Acceptance Criteria

MVP 只有同时满足以下全部条件才算完成：

1. 项目能在 macOS 14+ 开发者本机成功构建并运行。
2. App 不显示 Dock 主窗口入口，菜单栏图标、设置窗口和悬浮 HUD 正常工作。
3. HUD 固定 `420 × 44 pt`，布局为 Codex 图标、单行省略标题、红黄绿固定灯位。
4. HUD 首次位于主屏顶部居中，可拖到任意显示器，重启恢复，显示器断开后仍可见。
5. HUD 在所有空间和全屏应用中可用，任何状态变化和拖动都不抢当前键盘焦点。
6. 用户可从设置页安全安装、幂等修复和精确移除用户级 Traceflow Hooks，已有 Hooks 不丢失，非法 JSON 不被覆盖。
7. Codex CLI 与 Codex 桌面客户端均通过真实 Hooks 上报事件；双端任一未通过则不满足 MVP。
8. 事件映射严格符合本 PRD：黄为运行、红为审批、绿为完成、全灭为待机。
9. 绿灯 10 分钟后转待机，睡眠唤醒后按挂钟正确校验。
10. 新红灯抢占、红灯 FIFO、普通事件 FIFO、全局公平轮播和单会话行为全部通过自动测试与手动验证。
11. 所有已勾选待机会话仍继续轮播；无勾选项时显示 Traceflow 占位。
12. 会话复选框、单条删除、清空全部和再次发现行为正确，且不修改 Codex 对话。
13. App 重启后恢复偏好、位置、项目记录和勾选，所有运行状态恢复待机，对话摘要不恢复。
14. App 未运行时转发器快速安静退出，不自动启动 App、不保存离线事件、不明显拖慢 Codex。
15. Hooks 状态卡片能显示未安装、待验证、正常和异常，不把“文件存在”误称为“已信任”。
16. 日志按最多 5 个文件、每个最大 10 MiB 轮转，不按时间删除，且不记录禁用的敏感字段。
17. 标题生成、状态机、轮播、存储、Hooks 合并和日志轮转的规定测试全部通过。
18. 系统开启减少动态效果时，无红灯闪烁、黄灯呼吸和位移切换动画。

## 16. Out of Scope

- 普通 ChatGPT 桌面对话跟踪。
- Claude、DeepSeek 或其他 Agent 的实际适配；只预留 `agentType`。
- Windows、Linux 和跨平台框架。
- Mac App Store、App Sandbox、Developer ID 签名、公证、DMG 或自动更新。
- 开机自动启动。
- 数据库；第二版再评估 SQLite。
- 云同步、账号系统、远程监控和多设备同步。
- 完整 prompt、对话历史或 transcript 持久化。
- AI 生成对话标题或可靠读取 Codex 官方会话标题。
- HUD 点击展开、会话列表弹层或详情界面。
- 声音、系统通知、弹窗提醒和菜单栏状态动画。
- 自动审批或拒绝权限、修改工具输入、干预 Codex 流程。
- 离线事件队列、App 自动拉起和可靠消息重放。
- 搜索、分组、重命名、拖动排序和复杂批量会话管理。
- 用户自定义 HUD 尺寸、颜色、字体、主题和动画。
- 每个显示器各显示一个 HUD。

## 17. Further Notes

- 官方 Hooks 行为以 [OpenAI Hooks 官方文档](https://learn.chatgpt.com/docs/hooks) 和阶段 0 的本机实测为准。
- 官方文档明确指出 `SessionEnd` 始终同步执行；实现不得依赖其 `async` 配置。
- Hook 信任基于定义哈希。固定转发器路径和稳定命令字符串可以减少不必要的重新审核，但 Hook 定义变化后仍需用户重新执行 `/hooks` 信任。
- Unix Domain Socket 是本机 IPC，不应在文案中误称为“加密传输”。
- MVP 重点是验证可行性和用户体验，不追求分发完整度。
- PRD 获得用户明确批准前不得开始实施。实施时必须先完整阅读本文件，并按阶段在重大文件变更后等待用户确认。
