## 0. 文档执行规则

本文是本轮修复的正式开发规范，可直接交给低智能编码模型执行。实现者必须逐条完成数据保护、错误状态、交互、视觉、进程退出、Socket 超时和测试修复，不能只修改界面文案或只完成最容易观察的 HUD 样式。

本文覆盖历史文档中的冲突规则。明确覆盖项包括：

1. HUD 固定尺寸由 `420 × 44` 点改为 `420 × 40` 点。
2. 红灯由缓慢闪烁改为急促闪烁；黄灯继续使用柔和呼吸；绿灯常亮。
3. 未点亮的三盏灯不再使用统一灰色，而是分别保留低亮度红、黄、绿色底色。
4. 会话同步只请求用户正式会话来源，不再请求内部执行和子代理来源。
5. Hooks 正常状态不设置七天或其他时间过期规则。

继续保留已经确认的既有行为：菜单栏应用、无 Dock 图标、不自动启动、HUD 不抢键盘焦点、点击 HUD 本体不执行动作、标题单行尾部省略、项目二级列表、新会话默认不参与 HUD、所有待机会话仍轮播、日志最多五个文件且每个最大十兆、第一版使用本地 JSON 而不是数据库。

## Problem Statement

Traceflow 当前已经可以安装、启动、接收 Codex Hooks、同步会话并显示 HUD，但代码审查发现多个会破坏 MVP 可信度的问题：损坏的本地会话文件可能被下一条 Hook 静默覆盖；不同子系统共用同一个健康状态，真实故障会被覆盖；会话同步包含大量 Codex 内部记录；删除缺少确认；多显示器位置恢复不可靠；真实端到端脚本可能测试旧二进制且仍断言旧业务规则；进程和 Socket 在异常情况下可能无限等待。

同时，当前 HUD 虽然功能存在，但视觉上仍像普通浅色胶囊：毛玻璃透视不足，背景缺少压低干扰的灰色底调，灯位太小且红黄动画没有语义差异，无法达到用户给出的参考效果。

如果不先修复这些问题，后续功能会建立在不可靠的数据与验证基础上，用户也无法通过设置页准确判断到底是 Hooks、通信还是会话文件出了问题。

## Solution

本轮通过七组修复建立可信的 MVP 基线：

1. 为本地会话索引增加明确的健康状态和损坏只读保护，提供打开目录、备份并重建及自动重新同步能力。
2. 同步入口只读取正式用户会话，并在已知内部来源的 Hook 入口进行防御性过滤。
3. 将 Hooks 配置、本地通信和会话数据拆成独立健康状态，并精确核验完整 Hooks 定义。
4. 为单条删除和清空全部增加二次确认。
5. 使用真正的 macOS 原生毛玻璃容器重做 HUD 表面，并按确认尺寸增大灯位、缩小内边距、区分三种灯光动画。
6. 保存显示器身份与相对位置，使 HUD 在多显示器变化后完整可见。
7. 修正状态调度顺序、完成超时持久化、子进程总超时、Socket 读取超时和端到端脚本的新鲜度。

## User Stories

1. 作为已有正常会话数据的用户，我希望应用启动后继续读取全部 Traceflow 会话选择，从而保持 HUD 配置。
2. 作为会话文件损坏的用户，我希望原文件被完整保留，从而避免下一条 Hook 永久覆盖可供排查或恢复的数据。
3. 作为会话文件损坏的用户，我希望 HUD 和 Hooks 仍能运行，从而不因一个本地索引文件导致整个应用退出。
4. 作为会话文件损坏的用户，我希望设置页明确显示“会话数据损坏”，从而知道故障不在 Hooks。
5. 作为排查问题的用户，我希望一键打开 Traceflow 数据目录，从而查看或备份本地文件。
6. 作为需要恢复的用户，我希望点击“备份并重建”后保留损坏文件副本，从而可以安全建立新的会话索引。
7. 作为重建数据的用户，我希望应用自动重新同步 Codex 正式会话，从而无需手工触发第二步。
8. 作为重建数据的用户，我希望同步回来的会话默认关闭，从而不会让大量历史会话直接进入 HUD。
9. 作为遇到磁盘写入失败的用户，我希望设置页显示“无法写入”，从而不会误以为勾选和删除已经永久保存。
10. 作为使用 Codex 的用户，我希望会话同步只显示我直接创建的正式会话，从而不再看到大量内部执行记录。
11. 作为普通用户，我不希望看到“显示内部会话”的高级开关，从而保持 MVP 设置简单。
12. 作为管理会话的用户，我希望删除单条记录前获得二次确认，从而避免误删 Traceflow 本地索引。
13. 作为清理数据的用户，我希望清空全部记录前获得更醒目的二次确认，从而避免一次操作清空全部选择。
14. 作为担心原始对话的用户，我希望确认框明确说明不会删除 Codex 原始对话，从而放心执行本地清理。
15. 作为安装 Hooks 的用户，我希望设置页能识别缺失、定义不完整和配置正常，从而知道是否需要点击安装／修复。
16. 作为已经验证 Hooks 的用户，我希望正常状态不会仅因长期没有事件而自动变成异常，从而避免无意义告警。
17. 作为排查问题的用户，我希望分别看到 Hooks 配置、本地通信和会话数据状态，从而定位故障层级。
18. 作为排查问题的用户，我希望某一类状态刷新不会覆盖另一类错误，从而避免真正故障消失。
19. 作为使用多个会话的用户，我希望一次 Hook 状态变化只被调度器处理一次，从而避免错误抢占、重复排队或丢失展示。
20. 作为等待完成状态自动回到待机的用户，我希望新的更新时间被保存，从而重启后数据仍一致。
21. 作为同步会话的用户，我希望 Codex 服务异常时同步在有限时间内失败并恢复按钮，从而不会永久显示“正在同步”。
22. 作为使用 Hooks 的用户，我希望异常客户端不能永久占住本地 Socket，从而后续正常事件仍能进入应用。
23. 作为查看 HUD 的用户，我希望背景真正透出后方桌面和窗口并被模糊，从而获得原生毛玻璃效果。
24. 作为查看复杂桌面背景的用户，我希望毛玻璃上有轻微自适应灰色底调，从而让文字和灯光更清晰。
25. 作为浅色或深色模式用户，我希望 HUD 自动适配系统外观，从而不需要主题设置。
26. 作为查看运行状态的用户，我希望三盏灯足够大并占据灯区主要高度，从而能快速识别状态。
27. 作为查看待机状态的用户，我希望仍能辨认固定的红、黄、绿灯位，从而理解三盏灯的含义。
28. 作为需要介入权限请求的用户，我希望红灯急促闪烁并产生红色光晕，从而感到紧急且及时处理。
29. 作为等待任务执行的用户，我希望黄灯柔和呼吸并产生黄色光晕，从而理解任务仍在进行。
30. 作为任务完成的用户，我希望绿灯常亮并产生绿色光晕，从而明确知道任务已经完成。
31. 作为开启“减少动态效果”的用户，我希望灯光不闪烁、不缩放，从而避免不适，同时仍可静态识别状态。
32. 作为查看长标题的用户，我希望标题维持单行尾部省略，从而不改变固定 HUD 高度。
33. 作为正在输入的用户，我希望 HUD 更新、移动恢复和状态动画都不抢占键盘焦点。
34. 作为多显示器用户，我希望拖动后的 HUD 位置关联到所在显示器，从而下次启动仍出现在预期屏幕。
35. 作为调整显示器排列或分辨率的用户，我希望 HUD 保持相对位置并完整位于可见区域，从而不会只露出一角。
36. 作为拔掉外接显示器的用户，我希望 HUD 自动回到当前主屏幕顶部居中，从而不会丢失窗口。
37. 作为开发测试人员，我希望端到端测试每次使用当前源码的新构建，从而不会让旧二进制产生假结果。
38. 作为开发测试人员，我希望真实 Codex 端到端测试断言新会话默认关闭，从而与最新业务规则一致。

## Implementation Decisions

### 1. 模块边界

本轮应保持以下深模块和职责边界：

- 会话存储模块：负责 JSON 读取、原子写入、健康分类、写保护、备份和空索引重建。它不负责 UI，也不直接发起 Codex 同步。
- 会话来源策略：集中定义哪些 Codex 来源是正式用户会话，供 App Server 请求参数和防御性过滤共同使用，禁止在多个位置复制字符串数组。
- Codex 会话客户端：负责有限时长地启动服务、分页请求正式会话、解析结果和确定性结束子进程。
- Hooks 配置检查器：返回结构化检查结果，而不是只返回一个模糊布尔值；安装器继续负责幂等修复并保留其他应用的 Hooks。
- 应用协调模型：组合三类独立健康状态，协调 Hook、调度器、会话存储、重建与同步；任何存储错误不得写进 Hooks 状态。
- HUD 窗口与视图：窗口层负责真正的系统毛玻璃、非激活面板和跨屏位置；SwiftUI 内容层负责图标、标题、分隔线和灯光。
- 可靠性边界：Socket 模块保证单个异常连接有限时结束；轮播调度器只接收一次明确的状态变化；端到端脚本保证构建新鲜度。

### 2. 会话文件与健康状态

`sessions.json` 继续是 Traceflow 的本地索引，仍使用现有 JSON schema 版本。本轮不引入数据库，不保存对话正文、回答、工具输出或运行状态。

应用层必须公开独立的会话数据健康状态，至少包含：

| 状态 | 含义 | 设置页文案 | 是否允许保存 |
|---|---|---|---:|
| `healthy` | 文件不存在或已成功读取，最近一次写入也成功 | 正常 | 是 |
| `corrupted` | JSON 无法解码、schema 不支持或内容结构损坏 | 会话数据损坏 | 否 |
| `unwritable` | 有效数据在写入、替换或创建目录时失败 | 无法写入 | 否，直到显式重试成功或重启重新检测 |

读取规则：

1. 文件不存在视为正常空索引，不创建文件，直到第一次确实需要保存。
2. 文件存在且成功解码时载入会话并标记正常。
3. 解码失败或 schema 不支持时标记损坏，保留原始字节，不自动格式化、不自动截断、不自动写空数组。
4. 损坏后，所有普通保存入口必须在到达文件替换操作前拒绝写入。仅仅在日志中捕获异常不算完成。
5. Hook 接收和内存状态机可以继续工作；但是设置页必须显示当前改变不会被持久化，不能显示“保存成功”。
6. 损坏状态下禁用同步、会话勾选、项目批量勾选、单条删除和清空全部，避免制造无法保存的 UI 假象。Hooks 仍可更新内存运行状态，HUD 面板仍存在且不退出。
7. 写入失败时保留最后一个已知有效文件。后续自动保存不得反复覆盖或把健康状态改回正常。

设置页会话数据状态行必须提供：

- 所有异常状态均提供“打开数据目录”。
- 损坏状态提供“备份并重建”。
- 无法写入状态提供“重试保存”；重试使用当前内存持久化快照，成功后回到正常，失败则保留错误。
- 正常状态不显示修复按钮，只显示“正常”。

### 3. 备份并重建事务

“备份并重建”必须按以下顺序执行，不得颠倒：

1. 防止按钮重复触发，并显示进行中状态。
2. 再次确认当前源文件仍存在。
3. 将源文件复制到同一数据目录，文件名使用 `sessions.json.corrupt-<ISO8601 时间>-<短随机串>.backup`；时间中的冒号必须替换为可安全用于文件名的字符。
4. 读取源文件和备份文件并比较字节；只有完全相同才继续。
5. 通过临时文件和原子替换写入合法的空会话文档，不能先删除源文件。
6. 清空内存会话、轮播队列、当前 HUD 会话和项目展开键；重置下一轮播序号。
7. 将会话数据健康状态改为正常。
8. 自动发起一次正式会话同步。
9. 同步回来的全部新会话保持 `isIncludedInHUD == false`。
10. 若备份或空文件写入失败，停止流程，原文件保持不变，状态仍为损坏并显示可理解错误。
11. 若重建成功但随后 Codex 同步失败，保留合法空索引和备份，状态仍为正常；同步区域单独显示同步失败，可由用户重试。

不得自动猜测损坏 JSON 中可恢复的数组片段。MVP 的恢复策略只有“保留完整备份后重建”。

### 4. 会话来源过滤

正式会话来源白名单固定为：

- `cli`
- `vscode`
- `appServer`

App Server 的会话列表请求必须只发送以上三个 `sourceKinds`。不得再请求以下来源：

- `exec`
- `unknown`
- `subAgent`
- 所有以 `subAgent` 开头的细分来源

实现时必须把白名单放在一个纯逻辑策略中，供请求构造和测试读取。若响应对象提供来源字段，则解析为可选字段，并在导入前再次执行白名单过滤；若旧版服务没有返回来源字段，则以本次请求已限定的白名单为准，不因字段缺失拒绝正常会话。

Hook payload 中的 `source` 并不总是会话来源，正常事件可能缺失该值。因此防御性规则为：仅当新会话事件明确携带 `exec`、`unknown` 或以 `subAgent` 开头的来源值时丢弃；缺失来源的正常 Hook 事件继续处理；既有的 `compact` SessionStart 忽略规则继续保留。

本轮不增加“显示内部会话”开关，不增加数据库，不迁移或猜测旧记录的来源。开发测试环境可清空 Traceflow 本地索引或重新安装后验证新过滤规则。重复同步已有正式会话时，继续保留用户的 HUD 勾选和设置页排序时间。

### 5. 三类独立健康状态

设置页诊断区域必须显示三个互不覆盖的状态行：

#### 5.1 Hooks 配置

状态及语义：

- 未安装：既没有完整 Traceflow 配置，也没有可执行转发器。
- 需要修复：发现 Traceflow 配置或转发器，但至少一项定义不完整或不匹配。
- 待验证：完整配置已安装，但本地尚无成功收到的 Hook 或测试事件。
- 正常：完整配置已安装，且历史上至少成功收到一次 Hook 或测试事件。

一旦进入正常，不因七天或任何时间跨度自动降级。点击“安装／修复 Hooks”后重新写入定义并清除旧验证时间，因此回到待验证。用户仍需在 Codex 的 `/hooks` 页面完成信任。

#### 5.2 本地通信

状态及语义：

- 正常：Unix Socket 已成功创建并正在监听。
- 测试中：用户正在执行转发通道测试。
- 异常：Socket 启动失败，或本次转发通道测试明确失败／超时。

Socket 成功监听后可恢复为正常。测试失败不能把 Hooks 配置改成“需要修复”，因为配置检查与运行链路是两个不同事实。

#### 5.3 会话数据

使用前文定义的正常、会话数据损坏、无法写入状态。Hooks 安装、测试成功、同步成功或收到新事件都不得覆盖该状态。

### 6. Hooks 完整定义检查

配置检查必须逐事件验证全部必要字段。事件集合保持：`SessionStart`、`UserPromptSubmit`、`PermissionRequest`、`PostToolUse`、`Stop`、`Interrupt`、`SessionEnd`。

每个事件至少存在一个完全匹配的 Traceflow handler，完整匹配条件如下：

1. `type` 为 `command`。
2. `command` 等于对已安装转发器绝对路径进行 shell 安全引用后的值。
3. `timeout` 数值为 `3`。
4. `SessionStart` 的 group matcher 严格为 `startup|resume|clear`。
5. `SessionStart`、`UserPromptSubmit`、`PermissionRequest`、`PostToolUse`、`Interrupt` 的 handler 必须有 `async == true`。
6. `Stop` 与 `SessionEnd` 必须是同步 handler，即 `async` 缺失或明确为 `false`；不能接受 `true`。
7. 已安装转发器文件存在且具有可执行权限。

检查时允许用户配置中存在其他应用的 group 和 handler。只要 Traceflow 自己有一套完整匹配定义就判定完整；错误或旧版 Traceflow handler应使状态成为需要修复，安装／修复操作必须精确移除 Traceflow 旧定义后重新添加一份，不能删除其他应用配置。

配置检查器应返回缺失事件和字段不匹配原因，供日志及设置页简短错误说明使用。UI 不需要展示原始 JSON。

### 7. 删除确认

设置页维护两种独立确认状态：待删除的单条会话 ID，以及是否正在确认清空全部。不能在点击垃圾桶时立即调用删除方法。

单条删除确认：

- 标题：“删除此会话记录？”
- 正文：“仅删除 Traceflow 本地记录，不会删除 Codex 中的原始对话。”
- 破坏性按钮：“删除记录”
- 取消按钮：“取消”

清空全部确认：

- 标题：“清空全部会话记录？”
- 正文：“将删除 Traceflow 保存的全部本地会话记录和 HUD 选择，不会删除 Codex 中的原始对话。”
- 破坏性按钮：“清空全部”
- 取消按钮：“取消”

MVP 不显示“以后同步时可能再次出现”，不实现永久忽略列表。确认框使用原生 SwiftUI 确认对话框或警告框，必须支持 Escape 取消和键盘焦点，破坏性按钮使用系统危险角色。

### 8. Hook 事件与轮播调度顺序

每个被接受的正常 Hook 事件必须遵循唯一顺序：

1. 取得或创建目标会话状态机。
2. 将事件应用到状态机，得到旧状态、新状态和是否变化。
3. 将更新后的状态机写回内存字典。
4. 刷新发布给设置页的会话快照和项目分组，但该步骤不能再次把同一事件当作新的状态变化入队。
5. 用最新的会话集合更新调度器的成员、勾选集合和状态快照。
6. 对本次事件只调用一次状态变化报告；根据返回决策更新 HUD。
7. 若无切换决策但当前显示的就是该会话，则刷新当前 HUD 内容。
8. 在会话存储健康时持久化；不健康时跳过并保持相应错误状态。
9. 最后分别刷新 Hooks 配置状态和日志，不触碰会话数据健康状态。

允许通过拆分“只发布列表”和“更新调度器”来消除现有刷新方法的隐式副作用。禁止简单地在现有调用前后重复调用调度器以期碰巧正确。

完成状态十分钟超时回到待机时，必须：更新状态机、更新 `lastUpdatedAt`、向调度器报告一次变化、刷新 UI，并在存储健康时持久化一次。多个会话同一 tick 到期时只写一次文件。

### 9. App Server 生命周期与超时

会话同步必须同时具有“单次响应超时”和“整个同步总时限”：

1. 单次 initialize 或分页响应继续使用十五秒上限。
2. 从子进程成功启动开始计算整个同步总时限，固定为三十秒；分页数量不能无限延长总时间。
3. 每次等待响应使用“十五秒与总剩余时间中的较小值”。
4. 达到总时限后抛出同步超时，恢复同步按钮并显示失败信息。
5. 所有成功、失败和超时路径都清除 stdout／stderr 回调、关闭 stdin。
6. 正常请求结束后先给子进程一次正常退出机会；仍运行则发送终止信号，最多等待一秒；仍不退出则强制结束。
7. 禁止在没有截止时间的情况下调用阻塞式无限等待。
8. 终止过程不得在主线程执行。

分页去重、按更新时间排序和已有会话选择保留规则维持不变。

### 10. Unix Socket 读取边界

服务端接受连接后必须保证异常客户端无法永久占用串行监听队列：

1. 每个已接受连接设置一秒接收超时。
2. 继续限制单条消息最大一兆；超过后立即丢弃并关闭连接。
3. `read` 被信号中断时可以重试；收到 EOF 时处理完整非空数据。
4. 收到超时或其他不可恢复读取错误时丢弃未完成数据并关闭连接，不把半条 JSON 交给 handler。
5. 无论成功、超时、超限或错误，连接描述符都必须关闭。
6. 一个异常连接结束后，后续连接必须可以正常接收。

客户端现有的发送与 `shutdown` 行为保留。MVP 不改成网络服务，不开放远程连接。

### 11. HUD 原生毛玻璃

仅使用 SwiftUI 背景材质不足以保证无边框透明面板上的真实效果。窗口内容结构调整为：底层原生 `NSVisualEffectView`，上层透明 SwiftUI 内容视图。

原生效果视图要求：

- 使用适合 HUD 的系统材质。
- 混合模式为 behind-window，使 HUD 后方桌面和其他窗口真正参与模糊。
- 状态保持 active，不因前台应用变化而突然变成普通灰块。
- 图层圆角为 20 点并裁剪为胶囊。
- 面板本身继续透明、无边框、非激活、浮动、跨 Space、不显示 Dock 图标、不抢键盘焦点。

在毛玻璃之上叠加动态中性灰蒙版：

- 浅色外观使用黑色约 6% 透明度。
- 深色外观使用黑色约 18% 透明度。
- 蒙版必须允许后方内容继续可辨识地透出，不能退化成固定不透明灰色。
- 外沿叠加半点至一点的浅色高光描边；浅色模式透明度约 24%，深色模式约 16%。
- 保留轻微系统阴影，不增加厚重投影。

文字继续使用系统自适应前景色，必须在常见浅色和深色桌面背景上可读。参考图中的蓝色不是固定产品颜色。

### 12. HUD 固定布局

本版固定布局参数如下，不做用户尺寸设置：

| 项目 | 数值 |
|---|---:|
| HUD 总宽度 | 420 点 |
| HUD 总高度 | 40 点 |
| 胶囊圆角 | 20 点 |
| 左侧图标区宽度 | 40 点 |
| 标题区左右内边距 | 8 点 |
| 分隔线高度 | 22 点 |
| 单盏灯直径 | 20 点 |
| 灯间距 | 8 点 |
| 右侧灯区宽度 | 104 点 |

图标、标题、灯区顺序保持不变。标题单行、尾部省略、左对齐；长标题不得挤压灯区或改变 HUD 宽高。两条分隔线使用比当前更淡的半透明单像素线，保持区域提示但不切断玻璃整体感。

HUD 本体仍可拖动；普通点击不执行展开、设置或会话列表动作。

### 13. 状态灯视觉与动画

灯位固定顺序为红、黄、绿，任何状态下都不交换。

未点亮状态：

- 红灯使用红色约 18% 不透明度。
- 黄灯使用黄色约 18% 不透明度。
- 绿灯使用绿色约 18% 不透明度。
- 不产生外发光，不播放动画。

点亮状态：

| 会话状态 | 灯光 | 动画 | 光晕 |
|---|---|---|---|
| `attention` | 红灯 | 透明度在约 35% 与 100% 间急促往返，单程约 0.28 秒；不使用柔和慢呼吸 | 红色光晕随闪烁同步增强和减弱 |
| `running` | 黄灯 | 缩放约 0.94 至 1.06、透明度约 65% 至 100%，单程约 1.15 秒，使用柔和缓入缓出 | 黄色光晕柔和呼吸 |
| `completed` | 绿灯 | 无循环动画，保持常亮 | 稳定绿色光晕 |
| `idle` | 无灯点亮 | 无动画 | 无光晕 |

光晕半径继续受设置页低、中、高三档控制，但三档必须都能看出点亮与未点亮差别。灯光阴影不得被错误裁成方形。

系统开启“减少动态效果”时：

- 红、黄、绿点亮状态都使用静态 100% 亮度。
- 红灯不闪烁，黄灯不缩放，光晕不循环。
- 状态颜色、固定顺序和常亮光晕继续保留。
- 会话切换继续使用既有的无位移简化方案。

动画必须由当前状态驱动，快速切换状态时取消或替换旧动画，并明确落到新状态终值；不能依赖永远不会触发的动画结束回调。

### 14. 多显示器位置持久化

不再只保存全局绝对窗口矩形。新位置记录至少包含：版本号、显示器稳定标识、相对横向位置、相对纵向位置。

保存算法：

1. 用户拖动结束或窗口移动时，选择包含窗口中心点的显示器；若中心点不在任何屏幕，则选择与窗口相交面积最大的显示器。
2. 使用该显示器 `visibleFrame`，按“可移动范围”计算比例：横向分母为可见宽度减 HUD 宽度，纵向分母为可见高度减 HUD 高度。
3. 比例限制在 `0...1`，从而表示 HUD 左下角在该屏幕可移动范围中的相对位置。
4. 保存显示器标识和两个比例；不保存会导致布局变化失真的唯一绝对坐标。

恢复算法：

1. 找到已保存标识对应的当前显示器。
2. 找到时，用当前 `visibleFrame` 和当前 HUD 尺寸重新计算绝对位置。
3. 将整个 HUD frame 限制在该显示器可见区域内；“只有一点相交”不算可见。
4. 找不到目标显示器时，移动到当前主屏幕顶部居中，并立即保存新位置。
5. 没有任何保存记录时，同样使用主屏幕顶部居中，顶部保留 12 点间距。
6. 收到系统显示器参数变化通知时重新执行恢复／钳制，不能只检查矩形是否相交。
7. 读取到旧版绝对 frame 时允许一次性识别其主要显示器并转换为新相对格式；无法识别则回到主屏幕默认位置。

程序化恢复位置不得递归产生无限保存通知。HUD 继续跨桌面空间显示且不抢焦点。

### 15. 端到端脚本

本地 E2E 和真实 Codex CLI E2E 每次运行前都必须执行发布构建。禁止使用“二进制存在就跳过构建”的判断，因为它无法证明产物对应当前源码。

真实 Codex CLI E2E 的核心断言：

1. 临时 HOME 下启动当前发布版 Traceflow，并在有限时间内出现 Socket。
2. 真实 `codex exec` 触发 SessionStart、UserPromptSubmit、Stop 和 SessionEnd 链路。
3. 在有限时间内生成合法会话文件。
4. 文件中只有预期测试会话。
5. 项目名正确。
6. 新会话 `isIncludedInHUD` 必须为 `false`。
7. 成功时输出明确的通过文案；任何断言失败使脚本返回非零。

脚本继续使用临时目录并在退出时终止测试应用、清理临时数据。不得读写用户真实 Traceflow 数据。

## Testing Decisions

### 测试原则

- 自动化测试只验证可观察行为，不绑定私有函数、具体属性排列或 SwiftUI 视图层级。
- 纯业务逻辑、损坏保护、状态转换、超时与配置契约必须自动化。
- HUD 毛玻璃、灯光观感、确认框和多显示器使用编译检查加人工验收，不增加容易因像素差异失效的截图测试。
- 所有测试使用临时目录、假进程或本地 Socket，不接触用户真实 Hooks 和会话文件。
- 保留现有测试并修正与最新业务规则冲突的断言，不能通过删除测试获得通过。

### 自动化测试清单

#### 会话存储与恢复

1. 正常文件可往返读写，未知对话正文仍不落盘。
2. 损坏文件加载后进入损坏状态。
3. 损坏状态下模拟新 Hook 和普通保存，原文件字节完全不变。
4. 损坏状态下同步、勾选、删除和清空不会替换文件。
5. 备份并重建生成字节一致的备份和合法空文档。
6. 备份失败时原文件不变且不创建空文档。
7. 空文档原子替换失败时原文件和备份仍可用。
8. 写入失败进入无法写入状态，Hooks 状态不受影响。
9. 重试保存成功后回到正常状态。

#### 会话来源与导入

10. 正式来源集合严格等于 `cli`、`vscode`、`appServer`。
11. 会话列表请求不包含 `exec`、`unknown` 或任何 `subAgent*`。
12. 响应明确携带内部来源时被防御性过滤。
13. 新正式会话默认关闭；重复同步保留已有 HUD 选择和排序时间。
14. 明确来源为内部类型的新 Hook 不创建会话；来源缺失的正常 Hook 仍可创建会话。

#### Hooks 配置

15. 完整标准定义判定为已安装。
16. 每个事件分别缺失时都判定需要修复。
17. 错误 matcher、type、command、timeout 和 async 分别判定需要修复。
18. `Stop` 或 `SessionEnd` 被错误设置为异步时判定需要修复。
19. 转发器不可执行时判定需要修复。
20. 其他应用 Hooks 与一套完整 Traceflow 定义共存时仍判定正常。
21. 安装／修复两次仍只有一份 Traceflow 定义，其他配置保持不变。

#### 状态协调与轮播

22. 存储损坏后收到 Hook，Hooks 健康时间可更新，但会话数据仍显示损坏。
23. Socket 启动失败只改变本地通信状态，不覆盖 Hooks 和会话数据状态。
24. 非当前会话变红时只入队或抢占一次，不因列表刷新重复处理。
25. 当前会话状态变化时 HUD 内容刷新，队列不重复添加同一会话。
26. 多会话同一 tick 完成超时时只持久化一次，并保存新的 `lastUpdatedAt`。
27. 全部待机会话继续按轮播顺序切换。

#### 进程与 Socket

28. App Server 不响应 initialize 时在规定时限失败。
29. 某一分页不响应时受单次与总时限共同限制。
30. 进程忽略普通终止时执行强制结束，测试本身不能无限等待。
31. Socket 客户端发送半条数据后保持连接，一秒左右被服务端关闭且 handler 不收到半条消息。
32. 超时连接之后的正常连接仍能成功投递。
33. 超过一兆的数据被拒绝，后续正常连接不受影响。

### 构建与脚本验证

每个阶段至少运行与该阶段对应的 Swift 测试；最终阶段必须运行：

1. 全部 Swift 单元测试。
2. 发布配置构建。
3. 本地端到端脚本。
4. 真实 Codex CLI 端到端脚本；如果外部 Codex 环境不可用，必须记录具体外部阻塞，不能把本地脚本结果冒充真实 E2E。
5. 安装脚本的应用包结构检查，确保 HUD 容器变化没有破坏应用安装和重新打开。

### 人工验收清单

1. 在浅色桌面和深色桌面分别确认 HUD 能透出并模糊后方内容，且带轻微灰色底调。
2. 确认 HUD 为 `420 × 40`，灯直径明显为 20 点，内边距比旧版紧凑。
3. 确认两条分隔线更淡、更短，标题长时单行省略且灯区不移动。
4. 确认未点亮灯分别是暗红、暗黄、暗绿且无光晕。
5. 确认红灯急促闪烁、黄灯柔和呼吸、绿灯稳定常亮，光晕颜色正确。
6. 开启系统“减少动态效果”，确认三灯全部停止循环动画但状态仍清晰。
7. 拖动 HUD 不抢当前输入焦点；普通点击 HUD 无动作。
8. 在双显示器上拖动保存，重启后恢复到同一显示器近似相对位置。
9. 改变分辨率或显示器排列后，HUD 完整处于可见区域。
10. 拔掉 HUD 所在外接显示器后，HUD 回到主屏幕顶部居中。
11. 单条删除和清空全部均出现准确确认文案，取消不会改变数据。
12. 人工制造损坏会话文件后，设置页显示损坏，Hook 不覆盖文件，“打开数据目录”和“备份并重建”可用。
13. 三个健康状态同时展示，一个状态变化不覆盖其他状态。

## Acceptance Criteria

1. 损坏的 `sessions.json` 在启动、收到 Hook、点击同步或定时 tick 后字节仍不变。
2. 设置页可看到并区分 Hooks 配置、本地通信和会话数据三个状态。
3. “备份并重建”先生成可验证备份，再创建空索引并自动同步；所有新会话默认关闭。
4. 单条删除和清空全部都有二次确认，且文案明确不删除 Codex 原始对话。
5. App Server 请求只包含 `cli`、`vscode`、`appServer`，不再同步已知内部来源。
6. MVP 中不存在“显示内部会话”开关。
7. Hooks 任一事件定义的 matcher、type、command、timeout 或 async 错误都会显示需要修复。
8. Hooks 正常状态不因时间流逝自动降级。
9. 一次 Hook 状态变化只产生一次调度语义；完成超时变化会持久化。
10. App Server 和 Socket 异常均在有限时间内恢复控制，不存在无限等待路径。
11. HUD 使用真实原生毛玻璃和自适应灰色底调，固定尺寸为 `420 × 40`。
12. 三盏灯直径为 20 点，未点亮时分别呈暗红、暗黄、暗绿。
13. 红灯急促闪烁、黄灯柔和呼吸、绿灯常亮；对应光晕清楚且不过度。
14. 减少动态效果开启后无循环灯光动画。
15. HUD 在多显示器变化后完整可见，目标屏幕丢失时回到主屏幕顶部居中。
16. HUD 不抢键盘焦点，点击本体仍无动作。
17. 全部 Swift 测试、发布构建和本地 E2E 通过。
18. 真实 Codex CLI E2E 使用当前构建并断言 `isIncludedInHUD == false`。

## Out of Scope

- 数据库接入或会话 JSON 向数据库迁移。
- 自动修补损坏 JSON 或从碎片中猜测恢复部分会话。
- Hooks 健康状态七天过期、“需要复检”或后台周期检测。
- “显示内部会话”高级开关。
- 对旧内部会话记录进行来源迁移。
- 删除后永久忽略某个 Codex 会话。
- 删除确认中提示未来同步可能重新出现。
- HUD 点击展开会话列表或执行其他动作。
- 用户自定义 HUD 尺寸、灯直径、动画速度、背景颜色或主题。
- 开机自动启动。
- 修改现有日志轮转规则。
- 云同步、远程 Socket 或跨设备状态同步。
