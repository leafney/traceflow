# 会话日志上下文与清除确认 PRD

Related discussion: [`docs/discuss/2026-09-22-session-log-context.md`](../discuss/2026-09-22-session-log-context.md)

状态：已批准（2026-09-22）。

## 0. 编码模型执行约束

本文将交给低智能编码模型执行。下面各项均为强制要求：

1. 先完整阅读本文，再修改代码。只允许修改日志记录与“清除日志”确认交互；不得顺带重构 Hooks、会话状态机、轮播、日志轮转策略或设置页其它功能。
2. 只为**已被状态机接受**的普通 Hook 事件补充会话上下文。被丢弃的内部来源、无效 JSON、健康检查事件没有可靠会话快照，不得伪造项目或标题字段。
3. 保持现有日志轮转规则：最多 5 个文件，每个最大 10 MiB，按大小轮转；本需求不能改成按日期轮转。
4. 不记录用户提示词、完整对话、工具参数、工作目录绝对路径或未脱敏的异常数据。此需求的目标是定位会话，不是扩充诊断数据采集。
5. 删除日志必须由用户在第二个危险按钮上明确确认；第一个“清除日志”按钮不得直接删除文件。
6. 确认框取消、关闭或按 Escape 时必须不产生任何删除动作。
7. 使用现有 SwiftUI 设置页和已有的 `DestructiveConfirmation` 状态模式；不要引入第三方 UI 库、全局弹窗管理器或新的持久化字段。

## Problem Statement

当前日志只显示事件名和状态迁移，无法从一条日志判断哪个项目和会话触发了变化。设置中的“清除日志”按钮会立即删除日志，用户缺少防误触保护。

## Solution

在正常 Hook 状态迁移日志中补充项目名、会话 ID 和当前显示标题，并以安全的单行键值格式写入。将设置页的“清除日志”改为原生二次确认：说明删除范围，取消时不改动，确认时才调用现有轮转日志清理能力。

## User Stories

1. 作为查看诊断日志的用户，我希望每条正常状态变化日志都显示项目名，以便定位工作来源。
2. 作为查看诊断日志的用户，我希望每条正常状态变化日志都显示会话 ID，以便在同项目的多个会话间准确区分。
3. 作为查看诊断日志的用户，我希望每条正常状态变化日志都显示当前标题，以便无需查询数据文件即可快速识别会话用途。
4. 作为重视隐私的用户，我不希望日志因新增定位信息而记录完整提示词或对话正文。
5. 作为查看日志的用户，我希望一条 Hook 事件始终只占一行，方便文本搜索和命令行处理。
6. 作为准备清理日志的用户，我希望先看到清晰的影响说明，避免误删诊断资料。
7. 作为取消清理的用户，我希望点击取消、关闭弹窗或按 Escape 后所有日志文件保持不变。
8. 作为确认清理的用户，我希望当前日志和历史轮转日志一起被清除，但会话数据、HUD 设置、Hooks 配置和 Codex 对话保持不变。

## Implementation Decisions

### 1. 正常状态变化日志格式

仅修改“普通 Hook 事件被状态机接受后”的最终状态日志。日志必须保留既有字段并按以下固定顺序写入：

```text
event=<Hook事件名> state=<旧状态>-><新状态> project=<项目显示名> session_id=<会话ID> title=<会话标题>
```

示例（仅说明格式）：

```text
event=UserPromptSubmit state=completed->running project="traceflow" session_id="abc123" title="优化 HUD 灯光"
```

字段来源必须精确如下：

| 字段 | 来源 | 禁止来源 |
| --- | --- | --- |
| `event` | 已解码 Hook payload 的事件名 | 自行猜测的状态或 UI 文案 |
| `state` | 本次状态机应用结果的旧状态和新状态 | 轮播显示状态 |
| `project` | 已更新状态机快照的项目显示名 | `cwd` 的绝对路径 |
| `session_id` | 已解码 Hook payload 的 session ID | 缩写、哈希或设置列表序号 |
| `title` | 已更新状态机快照的当前显示标题 | 完整 prompt、完整对话正文 |

日志值编码规则：

1. 所有 `project`、`session_id`、`title` 值一律使用双引号包裹。
2. 值内的反斜杠写成 `\\`，双引号写成 `\\"`，换行、回车、制表符分别写成字面量 `\\n`、`\\r`、`\\t`。
3. 编码后不得包含真实换行或回车；一次 `logger.log(...)` 调用只能生成一条物理日志行。
4. 当项目名或标题为空时，写 `""`，不能省略字段、不能写 `nil`、不能改字段顺序。
5. 本轮不改变其它已有日志行格式，例如 `error=...`、`event=discarded ...`、同步结果、健康检查结果仍维持原样。

应用事件顺序必须保持原有逻辑：状态机接受事件 → 更新内存会话快照 → 调度 HUD → 持久化 → 写入含上下文的日志。日志读取的快照必须是本次事件处理完成后的同一个会话快照，不能在创建会话前读取，也不能从当前 HUD 轮播会话读取。

建议将“键值值安全编码”和“状态迁移行格式化”抽成无 AppKit／SwiftUI 依赖的核心纯逻辑。接口输入为五个字符串或状态值，输出为一条字符串；应用层只负责取得当前会话快照并写日志。这样可以单元测试空值、空白、中文、引号、反斜杠和换行，而无需启动桌面程序。

### 2. 清除日志二次确认

设置页“诊断”分区保留两个按钮：

- “打开日志目录”：行为不变。
- “清除日志”：保留 destructive 外观，但点击后只设置确认状态并展示原生 SwiftUI `Alert`，不能直接调用日志清理。

确认框内容固定为：

| 项目 | 文案／行为 |
| --- | --- |
| 标题 | `清除全部日志？` |
| 说明 | `将永久删除 Traceflow 的当前日志和历史轮转日志，不会删除会话记录、HUD 设置或 Codex 原始对话。` |
| 危险按钮 | `清除日志`；仅该按钮回调调用既有 `clearLogs()` |
| 次要按钮 | `取消`；不调用任何清理方法 |

现有设置页已经用一个可识别的危险确认状态管理“删除此会话记录”和“清空全部会话记录”。在该状态类型中新增一个明确的 `clearLogs` 分支；不要复用 `clearAll`，否则未来维护者可能把日志清理错误地当成会话清空。确认框必须纳入同一个 `.alert(item:)` 分支，确保同一时间只有一个危险确认框。

确认成功后不额外弹提示，不关闭设置窗口，不重启应用；现有日志清理器负责删除 `traceflow.log` 与 `traceflow.log.1` 至 `traceflow.log.4`（配置最大数为 5 时）。日志目录不存在时确认操作仍应安全完成，不能崩溃。

### 3. 不得回归的现有功能

- Hook 事件的接受、丢弃、状态迁移、HUD 轮播和会话持久化语义不变。
- 日志文件仍仅保存在 Traceflow 日志目录，并维持现有权限与异步串行写入方式。
- 清除日志不得删除会话数据文件、用户偏好、Hooks JSON、通知器可执行文件或 Codex 数据。
- “清空全部记录”仍只清会话记录，保留它自己的二次确认文案和行为；不得把它改为清日志。

## Testing Decisions

只为有边界条件的纯日志格式化逻辑与日志清理行为补充自动化测试；SwiftUI Alert 的真实点击流程使用构建检查和人工验收，不做脆弱截图测试。

1. 新增核心格式化测试，验证普通值的字段顺序和精确输出。
2. 测试中文项目名与标题可保留并被双引号包裹。
3. 测试双引号、反斜杠、换行、回车、制表符都会被转义，输出中不存在真实换行或回车。
4. 测试空项目名和空标题仍输出 `project=""` 与 `title=""`。
5. 保留并运行现有 `RotatingLogger` 测试，确认清除／轮转行为未回归；如新增清除测试，应使用临时目录，断言最多五个目标日志文件被删除且无其它文件被删除。
6. 运行 `swift test`、`swift build -c debug`、`git diff --check`。
7. 人工验收：触发一个普通 Codex Hook 事件，检查日志包含五个字段且能判断项目和会话；点击“清除日志”后先看到确认框，取消后日志仍在，确认后日志轮转文件消失，会话列表和 HUD 偏好仍存在。

## Out of Scope

- 不新增日志查看器、日志筛选、导出、按日期轮转、可配置日志级别或远程日志上传。
- 不改变日志保留上限、文件大小上限或日志目录。
- 不改变项目标题生成、会话同步、Hooks 安装／验证、权限请求状态或 HUD 灯光效果。
- 不新增对“打开日志目录”的确认，也不为其它非危险设置项增加弹窗。

## Further Notes

- 项目名和标题本身可能包含中文、空格与标点，固定双引号和转义不是可选美化，而是保证文本日志可安全逐行解析的要求。
- 本 PRD 只要求“状态变化日志”补充会话上下文；丢弃事件通常没有可信的已持久化会话，不应为了日志齐全而创建会话或泄露 cwd。
- 当前日志轮转策略已满足用户此前的“最多 5 个文件、每个最大 10 兆、不按时间轮转”要求，必须保持。
