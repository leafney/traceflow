# HUD 四种布局方向 PRD

Related discussion: [docs/discuss/2026-09-28-hud-four-layout-directions.md](../discuss/2026-09-28-hud-four-layout-directions.md)

> 状态：开发与自动验证已完成，待真实桌面人工验收。2026-09-28 按用户最新要求将图标隐藏阈值改为 80%。四个名称按三色灯组在 HUD 内的位置定义。

## 实施与验证记录

- 偏好：四布局值、旧横向／竖向值迁移与默认横向右已完成。
- 位置：四个独立键、首次复制、多屏身份保留、损坏数据回退及四端紧凑尺寸转换已完成。
- 界面：设置四项选择、HUD 三块重排、布局切换取消拖动及尺寸动画已完成。
- 自动验证：`swift test` 全量通过 165 项（新增最后一项位置键测试后共 166 项）；`swift build` 与 `git diff --check` 通过。
- 待人工验收：真实桌面四方向视觉、长标题、透明度动画、钉住鼠标穿透、外屏合盖唤醒与位置恢复。自动化测试无法代替这些桌面场景。

## Problem Statement

HUD 只提供横向与竖向两种排列，三色灯组固定在右端或下端。用户需要按桌面空间和阅读习惯，把灯组放在左、右、上、下四个端点，同时继续使用已有的透明度、图标隐藏、位置恢复与钉住功能。

## Solution

把设置中的“显示方向”改为“HUD 布局”的四项选择：横向左、横向右、竖向上、竖向下。选择后立即调整图标、标题和灯组的顺序，并恢复该布局上次的位置。旧横向／竖向设置分别迁移为横向右／竖向下。四种布局各自保存位置，新布局首次沿用相同方向已有位置。

## User Stories

1. 作为用户，我希望选择横向左，让灯组显示在标题左边，以适配当前桌面布局。
2. 作为习惯现有横向布局的用户，我希望横向右继续按图标、标题、灯组显示。
3. 作为用户，我希望选择竖向上，让灯组显示在标题上方。
4. 作为习惯现有竖向布局的用户，我希望竖向下继续按图标、标题、灯组显示。
5. 作为查看状态的用户，我希望灯组内部红黄绿顺序保持不变，以便快速辨认。
6. 作为阅读标题的用户，我希望标题区域始终位于另外两块之间，横向文字靠左、竖向文字靠上，以保持可读性。
7. 作为首次打开升级版的用户，我希望旧方向、旧位置立即正确显示，以免重新摆放。
8. 作为频繁切换布局的用户，我希望每种布局都恢复自己的位置，以免互相覆盖。
9. 作为刚选择新增布局的用户，我希望它首次出现在同方向已有布局的位置，以免跳到意料之外的屏幕。
10. 作为设置了高透明度的用户，我希望图标隐藏时灯组所在一端保持不动，以免状态灯跳位。
11. 作为在外接显示器上使用 HUD 的用户，我希望四种布局都遵循原有屏幕匹配和临时回退规则，以保持窗口可见。
12. 作为钉住 HUD 的用户，我希望切换布局时鼠标穿透和钉住状态继续生效。

## Implementation Decisions

### 排列与文案

- 布局唯一状态有四值：横向左、横向右、竖向上、竖向下。名称以灯组所在端命名，与窗口处于屏幕哪个角落无关。
- 横向左从左到右是灯组、标题、图标；横向右从左到右是图标、标题、灯组。
- 竖向上从上到下是灯组、标题、图标；竖向下从上到下是图标、标题、灯组。
- 灯组作为整体换端，组内从左到右／从上到下保持红、黄、绿；不镜像单灯顺序。
- 标题区域一直占中间。横向标题文字维持从左到右、区域内左对齐；竖向文字维持从上到下、区域内靠上。不要反转 Core Text 字形、标题内容或文字对齐方式。
- 图标尺寸、标题区域尺寸、灯组区域尺寸和总尺寸沿用现有规则。正常长轴 420 点，短轴 40 点；透明度达到 80% 后图标隐藏，长轴 380 点。横向左、竖向上只变区域顺序，不增加分割线。
- 设置的“HUD 布局”使用四项下拉 Picker，按上述顺序显示。首次安装默认横向右。切换立即完成，不增加布局切换动画。

### 兼容性与位置

- 已存储旧值 `horizontal` 和 `vertical` 必须分别解读为横向右和竖向下，首次读取后可写入新值；未知值回退横向右。不要把旧竖向用户改成竖向上。
- 旧横向位置记录属于横向右，旧竖向位置记录属于竖向下，旧数据不得删除、重命名后丢失或被新布局覆盖。新增布局使用独立位置键。
- 横向左第一次被选择时，以横向右的有效位置记录为种子；竖向上第一次被选择时，以竖向下的有效位置记录为种子。保留显示器身份与完整参考框的相对坐标；固定端字段必须转换为目标布局的端点语义，不能原样复制来源字段。不修改来源记录。之后两种位置独立保存。
- 如果对应旧方向没有有效位置记录，新增布局使用该方向现有默认位置算法，随后保存到自己的位置键。若来源记录损坏，不能把损坏数据复制到新键；沿用现有损坏记录的诊断和默认回退处理。
- 多显示器位置恢复、显示器丢失时临时显示在主屏、唤醒重试、用户拖动保存，均按当前布局自己的位置记录执行；临时回退不覆盖原显示器位置。
- 当前代码以完整尺寸参考框与紧凑尺寸显示框区分位置。扩展该几何策略：透明度达到 80% 时始终固定灯组一端，缩短图标所在端。横向左固定 minX；横向右固定 maxX；竖向上固定 maxY；竖向下固定 minY。由显示框反算参考框时，须精确逆向转换。
- 位置记录中现有固定端字段在新方向也必须按相同的完整参考框规则计算和还原。屏幕边缘反复展开／收起不得发生 40 点漂移；保存后重启亦然。
- 布局切换先取消正在进行的拖动和透明度尺寸动画，保留该手势开始前已保存的位置，再读取目标布局位置并立即显示。切换不隐式保存当前中途拖动位置。

### 实施模块

1. 偏好模块：将两方向扩展为四布局，集中描述方向、灯组侧、旧值映射与默认值。
2. 位置存储及几何模块：为四布局提供独立位置键、首次复制、尺寸变换和屏幕边界处理；保持旧记录可解码。
3. 应用模型及设置：暴露当前布局，Picker 显示四值并立即保存；其他设置不变。
4. HUD 视图：重排三个区域；标题文字对齐和灯组内部顺序保持原样。
5. HUD 窗口控制器：布局切换时取消手势及旧动画，按目标布局恢复尺寸与位置，不重置钉住、透明度和标题颜色。

### 给执行模型的逐项接线清单

1. 检查所有旧的 `.horizontal`／`.vertical` 精确比较、`switch`、位置键映射、默认框和尺寸逻辑。将“轴向”与“四种布局”分开理解，不要把新布局的两个横向值写到同一个位置键。
2. 处理 `@Published` 的时序：布局变化通知会早于属性存储变更。窗口切换逻辑以通知携带的新布局为准；需要重建 SwiftUI 内容时，延迟到模型存储已更新后执行，避免新窗口尺寸配旧排列。初次创建必须直接按已加载布局。
3. 对新布局的第一次加载，先确定自己的键是否存在。不存在时尝试从同方向旧布局的已解码记录生成目标布局记录；若没有有效来源，使用默认位置。生成动作只发生一次，不在以后每次切换时重做。
4. 四布局共享标题、灯组、图标组件，但只对三块区域排列顺序做调整。灯组三盏灯的 `ForEach`／调用顺序保持红黄绿，不能因为外层布局反向而反向。
5. 标题过渡方向按横向／竖向继续沿用现有行为；切换灯组侧不旋转文字、灯或图标。
6. 透明度 <80 与 ≥80 两种尺寸下分别核对四个固定端。尺寸动画 0.2 秒只用于跨越透明度阈值；四布局切换直接落位。系统“减少动态效果”继续立即完成。
7. 程序化位置恢复和尺寸变化不得写回位置记录；仅用户有效拖动结束、恢复默认位置等既有保存入口可保存。取消的手势不得保存。
8. 如果用户在横向左拖动，不能覆盖横向右的位置；竖向上与竖向下同理。旧用户启动后第一次显示应保持原有屏幕、位置与排列。

## Testing Decisions

- 用独立 UserDefaults 域测试旧 `horizontal`／`vertical` 值迁移、缺失或无效值回退、四个新值保存后重载。
- 测试四布局位置键分离、首次复制仅一次、来源缺失／损坏回退，以及旧位置仍由旧布局使用。重点验证外屏的显示器身份和相对坐标在复制后保留。
- 测试四布局在 79／80 透明度前后的参考框与显示框往返、四个固定端保持、屏幕边缘反复收起／展开及重启恢复。沿用现有几何和位置测试的独立模块方式，验证可观察输出。
- 对三个区域顺序建立可测试的布局描述；验证灯组始终在声明端点、标题居中、图标在另一端，灯组内部仍红黄绿。避免只测一个简单枚举映射却漏实际视图接线。
- 测试布局切换期间取消拖动、目标布局恢复自身位置；补充钉住、透明度和多显示器恢复的组合边界。
- 完整运行 `swift test`、`swift build`、`git diff --check`；真实桌面人工检查四布局、标题靠左／靠上、灯组顺序、图标隐藏及动画、拖动位置独立、多显示器唤醒。自动构建不能代替视觉验收。

## 低智能执行模型专用实现细则

### 1. 不可混淆的四个维度

| 界面名称 | 建议持久化值 | 轴向 | 灯组端 | 从左到右／从上到下 | 位置键 |
| --- | --- | --- | --- | --- | --- |
| 横向左 | `horizontalLeft` | 横向 | 左 | 灯组、标题、图标 | 新建 `hudPositionHorizontalLeftV1` |
| 横向右 | `horizontalRight` | 横向 | 右 | 图标、标题、灯组 | 沿用 `hudPositionHorizontalV3` |
| 竖向上 | `verticalTop` | 竖向 | 上 | 灯组、标题、图标 | 新建 `hudPositionVerticalTopV1` |
| 竖向下 | `verticalBottom` | 竖向 | 下 | 图标、标题、灯组 | 沿用 `hudPositionVerticalV1` |

- 表中英文值和新键是实现建议；即便采用其他命名，也必须保持一一对应并通过迁移测试。旧 `horizontal` 对应 `horizontalRight`，旧 `vertical` 对应 `verticalBottom`。正常偏好键仍为 `hudLayoutMode`，不要另加第二个互相竞争的布局键。
- 用布局的 `axis`、`lightsAtLeadingEdge` 或等价属性表达轴向与灯组侧；不要用 `layout == horizontalRight` 判定所有横向布局，也不要只根据轴向选位置键。
- 旧用户的 `hudPositionHorizontalV3` 和 `hudPositionVerticalV1` 必须原地继续使用，尤其不能把“横向左”写进 `hudPositionHorizontalV3`。已有旧 `hudPositionV2` → 旧横向键的迁移逻辑仍只属于横向右。
- 四布局的灯组内部顺序统一为红、黄、绿。横向左不允许 `HStack` 反向排列灯泡；竖向上也不允许 `VStack` 反向排列灯泡。

### 2. 排列的具体布局约束

- 三个区域沿长轴排列。灯组区域固定 104 点，标题区域固定 276 点，图标区域最多 40 点；通常为 `40+276+104=420`，图标完全隐藏时为 `276+104=380`。
- 横向左：`HStack(spacing: 0) { lights; title; icon }`；横向右：`HStack(spacing: 0) { icon; title; lights }`。两种情况下 `title` 仍使用相同的 `Text`、左对齐和截断规则。
- 竖向上：`VStack(spacing: 0) { lights; title; icon }`；竖向下：`VStack(spacing: 0) { icon; title; lights }`。两种情况下纵向 Core Text 标题始终从标题区域上端开始绘制，不翻转标题子视图。
- 可抽取共享的图标、标题和灯组区域视图；实际 SwiftUI 容器必须依该表重排。已移除的两条分割线不能重新出现。标题颜色 Switch 仍只作用标题。
- 图标隐藏阈值和动画使用已有 `hudIconFraction`。透明度等于 79 时图标占 40 点；等于 80 时目标占 0 点；中间动画帧占 `40 * hudIconFraction` 点。隐藏和展开只改变图标端区域，标题与灯组区域保持原尺寸。

### 3. 四种固定端的坐标公式

以下为 AppKit 屏幕坐标，Y 向上。完整参考框记 `C=(x,y,420,40)`（横向）或 `C=(x,y,40,420)`（竖向）；隐藏图标时 `d=40`，否则 `d=0`；显示框记 `F`。若处于透明度动画中，可把 `d` 扩展为 0～40 的连续值。固定端是**灯组所在端**。

| 布局 | 参考框 → 显示框 | 显示框 → 参考框 | 必须不动的坐标 |
| --- | --- | --- | --- |
| 横向左 | `F=(C.minX, C.minY, 420-d, 40)` | `C=(F.minX, F.minY, 420, 40)` | `minX` |
| 横向右 | `F=(C.minX+d, C.minY, 420-d, 40)` | `C=(F.maxX-420, F.minY, 420, 40)` | `maxX` |
| 竖向上 | `F=(C.minX, C.minY+d, 40, 420-d)` | `C=(F.minX, F.maxY-420, 40, 420)` | `maxY` |
| 竖向下 | `F=(C.minX, C.minY, 40, 420-d)` | `C=(F.minX, F.minY, 40, 420)` | `minY` |

- 先用未夹紧的 `C` 求 `F`，再按匹配显示器的 `visibleFrame` 夹紧 **显示框**。夹紧后的 `F` 不得在每次透明度切换后反推并覆盖未夹紧的 `C`，否则边缘会累计漂移。仅有效用户拖动松手或明确重置位置可建立新的 `C`。
- 位置记录当前有 `relativeX/Y` 和可选 `anchorX/Y`。旧横向右的 `anchorX` 表示完整框右端在可见屏宽中的比例；旧竖向下的 `anchorY` 表示完整框下端比例。新增横向左的 `anchorX` 必须表示完整框左端；新增竖向上的 `anchorY` 必须表示完整框上端。另一个轴继续沿用最小端。读写必须对称；不能按旧右端／下端公式解码新布局。
- 保存位置前把紧凑显示框按上表还原成完整参考框，再生成相对坐标和固定端字段。仅保存显示框原点会让高透明度重启后偏移 40 点。完整参考框可以在屏幕边缘外；显示框夹紧时不要覆盖保存记录。

### 4. 首次复制、外屏不可用和损坏记录

1. 选择横向左／竖向上时，先读取**目标键**。目标存在且有效：直接用它；不得从来源再复制。目标键存在但损坏：记诊断并走损坏数据回退，不允许每次用来源重建覆盖损坏数据。
2. 目标键不存在：读取横向右／竖向下的已解码有效记录。来源有效时生成**新记录**，保留显示器 UUID、旧显示 ID、名称、像素尺寸、完整参考框的相对坐标；目标固定端字段按目标布局重新计算。来源记录不得修改。
3. 来源显示器当前可识别时，使用来源记录和当前 `visibleFrame` 还原完整参考框，再计算目标固定端比例，确保新旧布局完整参考框位置一致；两种布局在同方向切换时应显示在同一屏幕相同参考位置。
4. 来源显示器当前不在系统中时，保留来源显示器身份及 `relativeX/Y`，把新记录的 `anchorX/Y` 留空，待显示器回来后按相对字段还原。此时 HUD 暂时显示在主屏，不能把主屏位置保存为目标键的永久位置。
5. 来源缺失：按同轴旧默认位置算法在当前主屏建立目标初始位置。来源损坏：记录诊断，不能复制无效数据；当前主屏上按默认位置临时显示，并依现有损坏恢复策略决定是否保存。不得修改来源键。
6. 将目标种子记录保存到目标键的时机是**确实获得有效来源且完成语义转换后**。若目标键缺失而外屏暂不可用，可保存相对字段且空固定端的新记录；显示器回来时不再重复复制。若来源也缺失，首次默认位置按现有缺失规则保存。
7. 旧值 `horizontal`／`vertical` 的偏好迁移不能删除旧位置键。旧用户启动时先读取偏好和对应旧位置，再创建窗口；第一帧必须保持此前布局与位置。

### 5. 布局切换和透明度变化的事件顺序

- Picker 变化 → 应用模型存入新布局 → 窗口控制器取得新布局 → 取消拖动 tracking、尺寸过渡计时器及迟到回调 → 以**目标布局**读取独立位置键／执行首次复制 → 算最新透明度对应的目标显示框 → 立即设置窗口 frame 和 SwiftUI 三块顺序。不要先把当前布局的中途 frame 保存到目标布局键。
- 现有模型使用 `@Published`，通知发出时属性的存储值可能尚未更新。处理器可以延迟到主队列下一轮；届时再次核对最新布局，快速连续切换时旧任务不能覆盖新布局。也可设计显式同步切换入口，但必须保证窗口 frame 与内容排列来自同一个布局值。
- 透明度 79↔80 时只改变图标区域和窗口长轴，用已有 0.2 秒动画；根据四布局固定端计算新 frame。布局切换发生在透明度动画中：取消旧动画，直接按新布局与当前透明度落到目标 frame，不能让旧回调把布局改回去。
- 拖动中切布局：取消该手势，保留旧布局**此前**已保存位置；目标布局恢复自己的位置。拖动结束后才切透明度阈值：先按手势实际显示形态保存当前布局的位置，再执行新阈值动画。
- 钉住、隐藏、显示、重置默认位置、显示器变化、唤醒均继续以当前四值布局读取／写入位置；钉住状态和鼠标穿透不因布局切换改变。无匹配屏幕时遵守既有主屏临时回退及重试，不覆盖原位置记录。

### 6. 必须跑的具体回归矩阵

| 场景 | 预期 |
| --- | --- |
| 旧 `horizontal` + 横向位置记录启动 | 显示横向右，旧位置与屏幕不变，旧记录仍在原键 |
| 旧 `vertical` + 竖向位置记录启动 | 显示竖向下，旧位置与屏幕不变，纵向文字仍从上向下 |
| 首次选横向左／竖向上 | 同方向旧参考位置作为种子；来源未被改变 |
| 新布局拖动后往返切换 | 四种布局各自恢复自己的位置，不互相覆盖 |
| 旧来源屏幕暂缺再连接 | 主屏临时显示；外屏回来后恢复原身份位置 |
| 旧来源或新目标记录损坏 | 不复制损坏数据，不无声覆盖损坏键 |
| 79→80→79，四布局各一次 | 灯组端的坐标不动，图标端缩短后展开 |
| 各布局在对应屏幕边缘反复切换阈值 | 不累计漂移；重启后恢复同一显示位置 |
| 布局切换时正在拖动／正在播放尺寸动画 | 旧拖动不保存，旧动画不回跳，新排列与 frame 同步 |
| 钉住且透明度 100 时切布局 | 背景保持透明、鼠标继续穿透、图标继续隐藏 |
| 长横向／纵向标题与占位标题 | 标题始终在中间，横向文字靠左、竖向文字靠上，灯序红黄绿 |

人工验收还要检查设置 Picker 的四项名称和顺序、外接显示器与合盖唤醒、不同透明度及标题颜色下的真实视觉结果。当前测试目标已有可复用的核心几何测试和 AppKit 视图测试，不必为简单的 Picker 文案写镜像测试。

## Out of Scope

- 不自动按屏幕边缘选择布局，也不自动吸附屏幕边缘。
- 不新增标题对齐方式、灯组内部顺序设置、布局切换特效或自动旋转文字。
- 不修改会话轮播、状态灯语义、背景透明度阈值、标题颜色、钉住鼠标穿透行为。
