# 灯体与光晕半径同步修订规格

Related discussion: [docs/discuss/2026-10-01-light-halo-radius-sync.md](../discuss/2026-10-01-light-halo-radius-sync.md)

状态：完整 PRD 已获用户批准，实施中；阶段验证并提交后连续执行。

## Problem Statement

用户观察到未点亮灯周围存在疑似残留光晕，以及灯体缩小时周围出现浅色分隔圈。用户希望保留灯体缩放，使光晕紧贴当前灯边，并随灯体增大而变浓、扩散，随缩小而收拢、变淡。

当前代码已有整体缩放、未点亮不绘制光晕，因此不能将截图原因直接断言为缺少缩放或条件判断。实现前须核对实际运行版本，原生验证须覆盖浅色背景与整个三灯区域。

## Solution

每帧只采样一次动画进度，计算灯体实际半径；再由实际半径计算光晕内侧衔接位置与外半径。以连续渐变代替独立描边光圈。光晕范围与不透明度同时随进度变化，最低点完全不绘制。灯体颜色、周期、55%～100% 明暗范围和未点亮 18% 保持。

## User Stories

1. 作为查看状态的用户，我希望灯体缩放时光晕始终贴着灯边，避免出现一圈背景色。
2. 作为观察闪烁的用户，我希望红灯暗段没有残留光晕，但仍能辨认当前点亮灯。
3. 作为观察呼吸的用户，我希望光晕随灯体变大而扩大、变浓，变化过程连贯。
4. 作为查看背景内容的用户，我希望未点亮灯保持 18%，没有自身光晕。
5. 作为选择标准或强烈效果的用户，我希望两种模式都有正确的尺寸同步，而强烈模式更清楚。
6. 作为使用减少动态效果的用户，我希望静态灯体与光晕仍正确衔接。
7. 作为使用横向或竖向布局的用户，我希望灯效变化不改变布局尺寸与灯距。

## 与旧规格的关系

本文批准后，覆盖 `docs/plan/2026-10-01-light-glow-animation.md` 中的光晕绘制规则：

- 替代固定 11～20 半径的增强渐变与直径 27 的独立描边。
- 替代对整个灯效应用 `scaleEffect` 的实现要求，改为直接绘制实际尺寸，防止重复缩放。
- 标准模式也采用动态半径及无缝衔接，旧的两层固定尺寸模糊实现不再是必须保留的规则。
- 保留原状态映射、灯体不透明度、动画相位、周期、峰值减弱决定、默认设置与保存行为。
- 旧网页是前版参考，不可作为本修订版的准确动画示范。

## Implementation Decisions

### 1. 用户已确认与建议值的区别

用户已确认：保留缩放、光晕贴边、强度及范围同步变化、最低点无光晕、未点亮 18%。以下衔接宽度、扩散宽度和渐变形状为本 PRD 的具体实现建议，需随本文审阅，尚未通过新的视觉对比定稿。

“由浅到深”指同一灯色的不透明度上升，不切换色相、不添加白色。单位为 macOS 逻辑点，网页预览使用对应 CSS 像素；Retina 像素倍率不得计入布局公式。

### 2. 状态与动画进度

沿用 `HUDLightAnimation.phase`；正常点亮情况下令 `p = phase`，范围为 0～1。

| 条件 | 灯体半径 R | 灯体不透明度 | 光晕进度 q | 是否绘制光晕 |
| --- | --- | --- | --- | --- |
| 未点亮，包括减少动态效果开启 | 13 | 0.18 | 0 | 否 |
| 点亮且正常动画 | `13 × (0.9 + 0.2 × p)` | `0.55 + 0.45 × p` | p | 仅 q > 0 时 |
| 点亮且减少动态效果 | 13 | 1 | 1 | 是，静态 |

减少动态效果时灯体保持现有基础尺寸，不变为最大动画尺寸；光晕范围使用 q=1，但衔接半径使用实际 R=13。

- 红灯周期 0.56 秒，保留原先上升、保持、下降、暗段的分段相位。
- 黄灯周期 2.8 秒、绿灯周期 2.3 秒，保留正弦呼吸相位。
- 所有尺寸、透明度必须来自同一次采样；不额外启动光晕定时器、不添加滞后动画。
- 当前帧的 `scale` 和 `glowIntensity` 可继续使用现有参数对象。用 `R = 13 × visual.scale` 与 `q = visual.glowIntensity`，不由灯体透明度倒推出 q。
- 未点亮判断优先于其他参数，即使调用方意外传入光晕峰值对象，`active == false` 也不能绘制光晕。

### 3. 光晕几何公式

建议衔接重叠宽度 O=1。标准最大扩散宽度为 4，强烈最大扩散宽度为 7：

```text
O = 1
W = (mode == standard ? 4 : 7) × q
innerRadius = max(0, R - O)
outerRadius = R + W
drawDiameter = 2 × outerRadius
```

W 是**超出当前灯体边缘的距离**，不是光晕总半径。q 为 0 时不绘制，不能留下半径 R 的亮边。q 上升时 R 和 W 同时增加；下降时同时收拢。

### 4. 连续渐变替代独立描边

不保留现有 `.stroke(...).frame(width: 27, height: 27)` 光圈；不添加新的描边。使用一层连续径向渐变，圆心与灯体圆心完全一致。

渐变采用 `startRadius: 0`、`endRadius: outerRadius`。将下列实际半径除以 outerRadius 转为 stops 的 0～1 位置：

| 渐变采样半径 | 标准峰值不透明度 | 强烈峰值不透明度 |
| --- | --- | --- |
| 0 | 0 | 0 |
| innerRadius | 0 | 0 |
| R | 0.35 | 0.63 |
| `R + 0.28 × W` | 0.28 | 0.56 |
| `R + 0.60 × W` | 0.12 | 0.175 |
| outerRadius | 0 | 0 |

- 非零不透明度均再乘 q。强烈系数已包含原峰值降低 30%，不再乘 0.70。
- 在 R-O 到 R 区间渐变从透明到灯边颜色，覆盖灯体边缘内侧的一点区域；在 R 到 outerRadius 连续衰减，不能中间插入透明带。
- 光晕中央透明，避免提升灯体中心实际合成不透明度；内侧重叠仅用于消除接缝。
- 新渐变不额外模糊，避免模糊重新制造空隙、外溢或改变覆盖范围；依靠渐变与原生抗锯齿产生柔光。
- q>0 时各停止位置递增；q=0 不生成渐变，避免重合停止位置。
- 不通过白色、黑色、阴影或混合模式补边。每一层只能使用当前灯的 `kind.color`。

### 5. 采样结果表

下表为正常点亮、强烈模式的建议值：

| p=q | 灯体半径 R | 灯体直径 | 灯体不透明度 | W | 光晕外半径 | 灯边不透明度 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 11.7 | 23.4 | 0.55 | 0 | 11.7（不绘制） | 0 |
| 0.25 | 12.35 | 24.7 | 0.6625 | 1.75 | 14.1 | 0.1575 |
| 0.5 | 13 | 26 | 0.775 | 3.5 | 16.5 | 0.315 |
| 0.75 | 13.65 | 27.3 | 0.8875 | 5.25 | 18.9 | 0.4725 |
| 1 | 14.3 | 28.6 | 1 | 7 | 21.3 | 0.63 |

标准模式 p=0.5 时外半径为 15，p=1 时为 18.3。减少动态效果下：标准外半径 17、强烈外半径 20。数字容许浮点误差 0.000001。

| `Sources/TraceflowApp/HUDView.swift` | 在 `StatusLightFrame` 由当前参数计算 R、q、W；重写光晕渐变；灯体直接用实际直径；移除整体缩放与旧绘制辅助函数 |

每帧推荐执行顺序：

1. 获取一次 `HUDLightVisualParameters`。
2. 根据 active 和 visual 计算实际灯体半径、不透明度。
3. 仅 active && q>0 时绘制相应模式的渐变。
4. 在光晕上方绘制灯体，使用实际直径 `2 × R`。
5. 外层继续 `.frame(width: 26, height: 26)` 作为布局占位，不能用光晕直径作为布局尺寸。
6. 删除 `StatusLightFrame` 原来的 `.scaleEffect(visual.scale)`，不能再缩放计算后的实际尺寸。

保持 `TimelineView` 30 帧刷新与暂停条件；保持状态灯固定身份，无需通过随机 `.id()` 强制重建。模式改变由现有模型发布更新驱动。

### 7. 未点亮和暗段清理

- 未点亮：仅绘制半径 13、不透明度 0.18 的灯体，无任何光晕视图。
- 当前点亮灯处于 q=0：仅绘制半径 11.7、不透明度 0.55 的灯体；不能把它误判为未点亮。
- 红→黄、红→待机后，红灯立刻采用未点亮规则；不保留旧描边或离场光晕过渡。
- 相邻点亮灯的光晕可能扩散至未点亮灯附近，因此“无自身光晕”需单灯和整组三灯分别验证，不能只靠截图判断状态分支。
- 若实际运行版本仍包含旧效果，先从当前提交构建验证，不在新逻辑中加入针对旧版本的补丁。

### 8. 窗口边界

强烈模式峰值光晕直径 42.6，大于浮条短轴 40。不得擅自扩大窗口、减小灯距或把灯区域改为光晕大小。须在四种布局的真实窗口中观察边界裁切；连续渐变在边缘已接近透明，但最终外观必须验收。

发现硬截边时记录复现帧、模式、布局、背景和运行提交，再提出缩小扩散宽度等方案。调整上述建议值需更新 PRD，不能自行添加遮罩或再次降低强度。

### 自动验证

1. 核心动画：原有三色周期、相位、55%～100%、未点亮 18%、减少动态效果优先级检查全部保留。
2. 原生固定帧：红黄绿分别渲染 q=0、0.25、0.5、0.75、1，在足够大的透明画布上检查灯体与光晕，避免测试画布本身截断。
3. q=0 和未点亮：灯体外侧无自身像素覆盖；未点亮中心 alpha 约 0.18，点亮最低点中心 alpha 约 0.55。
4. 贴边：q>0 时，在实际 R 附近多个方向采样，没有低 alpha 分隔带后又出现高 alpha 外圈的现象。排除抗锯齿容差，不断言每个像素的精确值。
5. 由小到大：相同模式下 q 上升时有效扩散半径递增、灯边 alpha 增强；建议以 alpha≥0.01 的有效覆盖像素衡量范围。
6. 中心透明：光晕不得把灯体中心 alpha 提升至高于公式结果；允许原生合成误差约 0.02。
7. 逆过程：相同 q 上升/下降帧几何一致，没有独立光晕时间源或滞后。
8. 模式与布局：保留真实 Hook/socket 集成测试；四种布局尺寸不变，标准/强烈的点亮画面不同，待机画面一致。
9. 减少动态效果：静态 R=13，强烈光晕外半径20，未点亮仍无光晕。
10. 状态清理：至少覆盖红→黄、红→待机、运行→完成；等待 SwiftUI 主循环处理发布更新后比较画面。

## 执行模型逐项编码说明

本节把上面的行为拆成确定的修改操作。当前真实入口是 `StatusLight → StatusLightFrame`，不要根据旧 PRD 在 `StatusLight` 内重新建立第二套绘制。不要复制旧 `enhancedGlow` 的固定半径或描边代码。

### A. 必须保留和必须删除

| 对象 | 操作 |
| --- | --- |
| `StatusLight` 的 TimelineView | 保留，一帧只调用一次 `HUDLightAnimation.parameters` |
| `StatusLightFrame` 的 kind、active、glow、visual 输入 | 保留，不修改外部调用契约 |
| `StatusLightFrame` 外层 `.scaleEffect(visual.scale)` | 删除，由实际灯体直径替代 |
| `StatusLightFrame` 的 26×26 外层占位 | 保留，不随动画变化 |
| 原 `enhancedGlow(intensity:)` | 删除或整体替换，不能保留独立 stroke 光圈 |
| 原 `glowLayer(...)` 和标准模式两次调用 | 替换为本修订统一渐变，不能与新渐变叠加 |
| `kind.color`、状态映射、周期和不透明度公式 | 保留 |
| 现有设置与用户保存的 `.standard/.strong` | 保留；不创建 `.vivid` |

两个模式共享几何算法，只使用不同的扩散宽度与渐变峰值。不能把标准模式遗留在旧的固定模糊代码中。

### B. 建议直接采用的帧几何代码

在 `StatusLightFrame` 内定义私有计算属性，避免多个绘制层分别重复计算。下面的基础半径来自现有 `HUDMetrics.lightDiameter`，不要再定义一个不同的灯体基准。

```swift
private var bodyRadius: CGFloat {
    let base = HUDMetrics.lightDiameter / 2
    return active ? base * CGFloat(visual.scale) : base
}

private var bodyOpacity: Double {
    active ? visual.bodyOpacity : 0.18
}

private var haloProgress: Double {
    active ? min(1, max(0, visual.glowIntensity)) : 0
}

private var haloWidth: CGFloat {
    (glow == .strong ? 7 : 4) * CGFloat(haloProgress)
}
```

`visual` 必须仍由生产动画模块生成，不能把测试帧参数接入实际界面设置。`haloProgress` 是进度，不是半径；`haloWidth` 是灯体边缘以外的扩散距离。

绘制结构建议如下：

```swift
var body: some View {
    ZStack {
        if active && haloProgress > 0 {
            synchronizedHalo
        }
        Circle()
            .fill(kind.color.opacity(bodyOpacity))
            .frame(width: bodyRadius * 2, height: bodyRadius * 2)
    }
    .frame(width: HUDMetrics.lightDiameter, height: HUDMetrics.lightDiameter)
    .accessibilityHidden(true)
}
```

不要在以上结构的任何一层重新加 `.scaleEffect`、`.animation` 或 `.transition`；动画时钟已经逐帧提供尺寸。不要添加整个 ZStack 的 `.opacity`。默认 ZStack 中心对齐足够，不给灯体或光晕增加 offset。

### C. 渐变参考代码

下面代码完整表达拟采用的连续光晕。它只应在 `haloProgress > 0` 时访问，此时 `haloWidth > 0`，stop 位置不会因为 q=0 重合。

```swift
private var synchronizedHalo: some View {
    let radius = bodyRadius
    let width = haloWidth
    let outer = radius + width
    let inner = max(0, radius - 1)
    let q = haloProgress
    let strong = glow == .strong
    let edge: Double = strong ? 0.63 : 0.35
    let near: Double = strong ? 0.56 : 0.28
    let far: Double = strong ? 0.175 : 0.12

    return Circle()
        .fill(RadialGradient(
            stops: [
                .init(color: .clear, location: 0),
                .init(color: .clear, location: inner / outer),
                .init(color: kind.color.opacity(edge * q), location: radius / outer),
                .init(color: kind.color.opacity(near * q), location: (radius + 0.28 * width) / outer),
                .init(color: kind.color.opacity(far * q), location: (radius + 0.60 * width) / outer),
                .init(color: .clear, location: 1)
            ],
            center: .center,
            startRadius: 0,
            endRadius: outer
        ))
        .frame(width: outer * 2, height: outer * 2)
}
```

注意 `startRadius` 必须为 0，因为 stops 已经把真实半径换算成 `真实半径 / outer`。如果又设置 `startRadius: inner`，会重复偏移，光晕与灯边无法正确衔接。

不要把位置 `(radius + 0.28 * width) / outer` 简写成 `0.28`；0.28 表示相对于**灯体边缘之外的扩散宽度**，不是整个光晕圆的28%。

这层渐变中央透明，在灯边内侧1点范围内变浓，到灯边达到峰值，再向外渐淡。灯体必须最后绘制在上面。光晕强度乘 q 一次；原来降低30%的决定已经体现在0.63等峰值中，不能再乘0.70。

### D. 用数值验证几何是否接对

强烈模式 q=0.5 时：

```text
R = 13
W = 3.5
inner = 12
outer = 16.5
frame = 33 × 33

stop 半径：0、12、13、13.98、15.1、16.5
stop 位置：0、0.7272727、0.7878788、0.8472727、0.9151515、1
stop alpha：0、0、0.315、0.28、0.0875、0
```

灯体在同一帧直径26、alpha0.775。从半径12到13渐变衔接，不能在13到13.98之间插入透明色。中心区域光晕透明，灯体中心alpha应接近0.775，而不是因为后方光晕叠加而超过这一值。

强烈模式 q=1 时：灯体直径28.6，光晕直径42.6；**占位仍为26×26**。这不是几何冲突：SwiftUI 的外层 frame 规定布局尺寸，内部图形可超出占位绘制。不要为了容纳光晕扩大 HStack/VStack 的灯间距离。

### E. 现有测试应如何调整

当前 `HUDLightRenderingTests` 把峰值帧渲染到64×64透明画布，并以中心(32,32)采样。这一方法可保留；64足够容纳直径42.6的光晕。

1. 保留当前静态、未点亮、26×26占位和真实Hook测试。
2. 更新旧的“半径16～19环带平均alpha”阈值：新标准外半径18.3，强烈21.3，必须按新效果验证，不为通过旧阈值恢复旧模糊或旧描边。
3. 增加三色低中高固定帧，显式指定当前正确的 `scale/bodyOpacity/glowIntensity`；不要让 `TimelineView` 实时时钟决定这些测试帧。
4. 在足够大的画布上检查中心alpha、外侧透明区和贴边区域，保持像素容差，不比较整个PNG文件的逐字节结果作为渐变连续性证明。
5. 对真正的 `.idle` 状态继续使用 `active:false`，而不是 `.running` 的q=0。两者灯体尺寸与alpha不同，必须分别验证。

### F. “没有间隙”的可执行验证方法

像素是离散且有抗锯齿的，不能简单要求所有像素alpha>0，也不能凭一张缩略截图通过验收。

建议原生固定帧像素检查：

1. 使用 `ImageRenderer`，scale=2，渲染64×64逻辑点，得到128×128像素；实际采样圆心为(64,64)。图像读取索引必须乘2，不能沿用原scale=1的32中心。
2. q使用0.25、0.5、0.75、1；q=0单独验证光晕完全消失。
3. 在八个方向（每45度一个）从R附近向外采样，采样单位保持逻辑点，取附近小区域均值减小抗锯齿噪声。
4. 观察灯体边缘到外渐变的alpha分布。若出现连续至少1个逻辑点的alpha<0.01透明带，随后又出现alpha≥0.03的可见光圈，判为间隙失败。弱光帧本就很淡，不能把自然衰减到透明误判为间隙。
5. 在超过outer至少2个逻辑点的区域应接近透明；q=0时从R+2开始应近似透明。
6. 中心半径0～8区域均值应接近灯体目标alpha，容差0.02；未点亮为0.18，点亮最低点为0.55。
7. 有效范围可用alpha≥0.01的覆盖像素计算，q上升时范围应扩大；每种颜色分别比较自身帧，不跨颜色比较RGB亮度。

注意：RGB颜色在透明图像中可能预乘alpha，因此连续性以alpha为主；浅色背景下的白圈仍需将图像叠到浅灰底或在实际窗口人工观察。对称几何测试不能替代原生窗口边界裁切验证。

### G. 真实状态更新与异步采样

复用 `SessionIntegrationFixture`，不要直接修改 `AppModel.displayedSession` 的私有 setter，也不要向用户真实socket发送测试事件。

```text
userPromptSubmit → running
permissionRequest → attention（红）
stop → completed（黄）
interrupt → idle（全部未点亮）
```

最少覆盖“permissionRequest→stop”（红转黄）与“permissionRequest→interrupt”（红转待机）两条路径。状态检查使用真实模型，图像检查使用生产 `HUDView`。等待模型处理对应事件，再等待SwiftUI主循环刷新；同一同步调用内抓取缓存图像不算刷新验证。

动态红灯正好落在q=0时，标准和强烈画面本来就应相同。不能对任意实时时刻断言两模式必定不同。模式差异用固定q>0帧验证；真实HUD测试主要验证状态变化、清理和布局尺寸。
