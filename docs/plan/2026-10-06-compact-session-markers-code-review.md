## 一、优先修复：旧会话批量补色阻塞启动与同步

位置：`Sources/TraceflowCore/SessionMarkerColor.swift` 的 `allocate`、`fillingMissing`；`Sources/TraceflowApp/AppModel.swift` 的 `fillMarkerColors`、`restoreSessions`、`mergeCodexThreads`。

每补一个颜色，重新扫描整个候选池，并与此前所有占用颜色计算距离。批量 m 条缺颜色会话、n 条已有颜色、C 个候选时，核心距离计算约为 O(C×(m×n+m²))。分色在主线程上的 AppModel 启动恢复和同步回调中同步执行，期间菜单、HUD、套接字主线程处理都会等待。

使用当前源码独立编译 `swiftc -O`，在临时目录中构造旧会话测量：

| 缺颜色会话数 | 补色时间 | 分配结果 |
| --- | --- | --- |
| 100 | 0.647 秒 | 100 个不同颜色 |
| 300 | 2.113 秒 | 300 个不同颜色 |
| 600 | 6.187 秒 | 600 个不同颜色 |

这是本机优化编译下的单轮测量，不是正式性能门槛。问题无需百万会话即可触发；同步历史会话或首次升级补色时即可出现。

修复方案：

1. 在一次批量补色中创建分配器，预先解析候选 RGB；针对初始占用色，只计算一次每个候选的最小距离。
2. 每选中一个新颜色，只将各候选的已缓存最小距离与这个新颜色的距离取 min；保留候选顺序、评分公式与同分选择规则。将重复计算降至约 O(C×(n+m))，不改变产品分色规则。
3. 使用循环求最小值，避免每个候选反复创建 `channels.map` 临时数组及重复正则解析。
4. Hooks 接入只在新增／缺颜色时触发补色。当前每个接受的 Hook 都调用全量 `fillMarkerColors`，即使全部颜色已存在，也会扫描、规范化、排序并写回全部状态机。这不是重复分配，但属于不必要的事件开销。600 条已着色会话处理 100 次全量补色的纯函数耗时约 0.536 秒。
5. 若优化后大批量仍超出响应预算，再移到后台处理，使用元数据版本校验合并结果，不能覆盖计算期间用户修改的颜色、删除或新导入记录。

补测：新旧算法在预览色、任意已有色、重复手动色、乱序批次及候选耗尽情况下输出一致；600／更大批次测耗时；普通 Hook 不执行全量补色；异步方案还需测试处理中用户改色与删除。

## 二、需要修复：连续选色每次同步保存全部会话

位置：`Sources/TraceflowApp/SessionColorPanelController.swift` 的 `save`；`Sources/TraceflowApp/AppModel.swift` 的 `setMarkerColor`；`Sources/TraceflowCore/SessionStore.swift` 的 `save`、`writeDocumentUnlocked`。

颜色面板开启连续通知，每个不同 RGB 都同步调用 `setMarkerColor`。该方法在主线程构造和排序全量记录，SessionStore 虽有私有串行队列，但使用 `queue.sync`，主线程仍等待完整 JSON 编码、回读验证和原子文件替换。拖动选色控件产生连续事件时，会连续阻塞界面与轮播。

同样使用 `swiftc -O`，真实临时文件连续保存 30 次，本机平均耗时：

| 保存会话数 | 单次保存平均耗时 |
| --- | --- |
| 100 | 13.75 毫秒 |
| 600 | 40.63 毫秒 |
| 2000 | 76.57 毫秒 |

这些仅为 SessionStore 的耗时，尚不包括 AppModel 排序、发布列表和界面重绘。已有“同颜色直接返回”只能去掉相同值事件，无法缓解不同颜色的连续通知。

修复方案：

1. 建立统一的串行异步保存协调机制，将磁盘工作移出主线程；所有会话保存路径需遵守同一版本／顺序规则，不只给选色器随手加一个后台任务。
2. 按会话 ID 与选色绑定代次管理请求，将尚未开始的连续选色请求合并为最新颜色；已执行的写入不乱序。成功落盘后才发布对应颜色，保留当前“保存失败不显示未保存新色”的行为。
3. 关闭面板、切换编辑目标、关闭设置、退出时保证最后一次选色请求被处理；删除目标时取消对该目标的待处理请求，禁止旧请求重建会话。
4. Hook、同步、删除和标题编辑可能同时改变记录，后台任务不得用过期的全量快照覆盖这些变化；使用统一写入协调器的最新记录集合和版本检查。
5. 如果选择先用限频／事件合并简化实现，应先补充 PRD 的实时保存与关闭刷新规则；不要静默将连续保存改成“松开鼠标才保存”。

补测：快速连续选色最终值正确；保存乱序或失败不发布错误色；编辑 A→B 的旧回调不能修改 B；删除与待保存请求交错不重建记录；并发 Hook／标题修改不丢失；关闭和退出保留最后选择。

## 五、审查后修复记录

用户随后授权直接修复上述两项中高优先级问题。以下为实际整改，前文测量保留为修改前基线。

### 批量分色

- 采用候选 RGB 和候选最小距离缓存，每加入一个颜色只更新一次各候选评分；有颜色的普通 Hook 不再全量补色。
- 已有合法颜色全部保留，排序、候选顺序、评分公式、同分选择和候选耗尽降级不变。
- 增加旧规则参考算法测试，对空集合、任意已有色、重复手动色、灰色、小写色、乱序／相同轮播序号和候选耗尽批次逐条比较，输出一致。

同机同入口 `swiftc -O` 单轮测量：

| 缺颜色会话数 | 修改前 | 修改后 |
| --- | --- | --- |
| 100 | 0.647 秒 | 0.026 秒 |
| 300 | 2.113 秒 | 0.031 秒 |
| 600 | 6.187 秒 | 0.055 秒 |

600 条约提升 112 倍；首轮包括候选缓存初始化。此结果为本机测量，不是跨设备性能保证。已着色 600 条全量处理 100 次降至 0.185 秒，常规 Hook 已直接跳过这条分色路径。

### 连续选色与统一保存

- 主线程只管理记录、编辑请求与写入顺序，磁盘编码、校验、原子替换由 SessionStore 的后台串行队列处理。最多一个写入在途，等待中的同一会话选色合并为最新值。
- 开始写入时取最新全量元数据；成功回调只合并对应颜色／标题字段。新增 Hook、开关、标题、同步和删除不会被旧快照覆盖。
- 连续编辑保留同一编辑批次标识；删除后重建会话会开始新批次，旧结果不能修改新会话。若前一颜色已成功、后一颜色失败，界面保留前一已保存颜色，与磁盘一致。
- 关闭面板、切换会话或关闭设置不撤销已接受的颜色请求；面板绑定代次防止旧回调关闭新目标的面板。
- 标题编辑显示保存中并禁止重复提交；恢复默认标题也走相同队列。失败保留原值和草稿。
- 手动同步、重试仅在实际保存完成后显示结果。退出先停止新事件，再异步等待队列排空；测试清理使用同步屏障，并使旧主线程回调失效。
- 七项受控慢写测试已验证请求合并、关闭／切换目标、并发 Hook 和标题、删除后同 ID 重建、失败重试、退出与清理。包含中间颜色成功、最终颜色失败的专门测试。

上述修改没有部署应用；前文列出的真实跨屏与实屏合成验收仍需具备环境者完成。
