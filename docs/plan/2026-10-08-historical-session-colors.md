# 历史会话颜色优化

日期：2026-10-08
状态：功能方案已批准；本文补充编码交接细节，不改变已确认业务范围

## Problem Statement

目前启动恢复和同步会为全部无颜色会话分配唯一颜色。大量长期未活动会话也参与候选颜色距离评分，增加首次历史导入、补色时的计算量。旧版已分配的历史颜色同样扩大占用集合。用户希望历史会话显示灰色，并在既有会话处理流程中自动清理颜色，无需额外操作按钮。

## Solution

统一采用最近 7 天颜色策略：超过 7 天的会话清空颜色，显示现有灰色标记；7 天内已有颜色保持不变，无颜色才分配新颜色。启动恢复、后台自动发现、手动同步统一处理全部已加载记录；历史会话重新活跃后可恢复分配颜色。

取消独立重置按钮及确认弹窗。设置页继续使用现有“同步 Codex 会话”。不清空会话记录。

## User Stories

1. 作为首次使用者，我希望同步的历史会话直接显示灰色，以减少不必要的颜色计算。
2. 作为已有用户，我希望启动或同步自动清理旧版历史颜色，以获得相同优化。
3. 作为用户，我希望近期会话已有颜色稳定保留，以维持识别习惯。
4. 作为用户，我希望近期新发现或缺少颜色的会话自动补色，以区分会话。
5. 作为用户，我希望旧会话重新活动时恢复颜色，以便识别正在使用的会话。
6. 作为用户，我希望现有同步入口完成颜色维护，避免增加重复按钮。
7. 作为用户，我希望清理颜色保留标题、项目和 HUD 勾选，以免影响其他设置。
8. 作为用户，我希望颜色持久化与显示保持一致，保存失败得到明确反馈。

## Implementation Decisions

### 时间与颜色规则

- 使用最后活动时间，缺失时回退最后更新时间；不使用创建时间或列表排序时间。
- 历史条件为当前时间减有效活动时间严格大于 604800 秒。恰好 7 天属于近期；未来时间不判历史。
- 每次策略调用注入同一个当前时间，便于边界一致和固定时间测试。
- 先清空历史颜色，包括手动颜色。空值代表无特定颜色，使用现有灰色 `#808080` 回退；不为历史记录存储灰色值。
- 历史记录不进入占用颜色集合，不参与颜色距离评分，也不获得新颜色。
- 近期有效颜色保持不变；缺失或无效颜色沿用原有稳定批量分配顺序补齐。自动分配避开近期已有及本批新分配颜色。
- 近期手动重复颜色仍可保留；自动分配唯一性不意味着强行修复已有手动重复。
- 批次没有需要补色的近期记录时，不初始化颜色分配器；历史颜色清理仍执行。
- 不要求重新活跃后的颜色与清理前相同；不引入颜色来源字段或修改存储结构。

### 处理入口

- 启动恢复：读取后，对全部恢复记录执行统一策略。
- 后台自动发现和手动同步：先合并最新活动时间，再对全部已加载记录执行统一策略，包括本次结果未包含的本地记录。
- 有效 Hook：先应用事件更新活动时间，确保当前无颜色会话可恢复补色；策略被调用时同时清理其他历史记录。
- 不因每次界面渲染启动分配，不新增专门到期计时器。不承诺跨越 7 天的瞬间立即变灰，下一处理入口负责刷新。
- 保留手动颜色选择能力，不新增历史颜色编辑限制；后续统一处理会再次清理仍属历史的颜色。

### 保存、并发与展示

- 沿用会话写入队列与数据健康保护；清理结果保存后，重启仍为空颜色。
- 集成时审查正在保存的手动颜色，避免旧回调把历史颜色重新写回；以最新活动时间和有效写入顺序决定最终结果。
- 修改单个颜色的现有“保存成功才发布、失败保留旧颜色”行为继续有效；新增清理遵循现有启动和导入保存模型，失败提示，不宣称成功。
- 保存不得用旧会话快照覆盖期间到达的 Hook 活动时间、标题、启用状态、删除或其他元数据。
- 列表、置顶区、当前 HUD 的颜色读取保持一致，不因颜色清理切换会话或重启轮播周期。
- 不修改标题、活动时间、排序时间、项目、HUD 勾选、运行状态。

### 模块划分

1. 核心颜色策略：封装历史判定、清理、近期占用集合及补色，继续使用既有分配算法。
2. 应用模型：接入恢复、发现合并及 Hook 流程，维护写入与发布一致性。
3. 现有渲染：复用空颜色灰色回退；设置页不新增控件。

## Testing Decisions

不采用 TDD。测试聚焦时间边界业务逻辑与异步保存状态，沿用现有颜色分配和写入队列测试方式；使用固定时间，不真实等待 7 天，不断言私有数据结构。

必要覆盖：

1. 7 天前后及恰好 7 天；未来时间；活动时间缺失回退。
2. 最后活动时间优先于最后更新时间，完成超时不会把历史会话错误判近期。
3. 历史无颜色保持为空；历史已有颜色包含手动颜色被清空。
4. 近期已有颜色保留；近期空颜色稳定补齐，自动颜色互不重复且避开占用。
5. 只有历史记录时不生成颜色；混合批次的近期分配结果与剔除历史记录后的结果一致，证明历史颜色不参与评分或占用。
6. 重复执行幂等；不改其他元数据。
7. 启动恢复、自动发现、手动同步均执行同一策略；导入更新活动时间后正确补色。
8. 历史会话收到有效 Hook 后获得颜色；无效或重复事件不制造虚假活动。
9. 清理保存成功可重新读取；失败反馈、手动颜色待保存期间的清理及写入期间的 Hook 不造成旧颜色或旧元数据回写。

验证执行 `swift test`、`swift build`、`scripts/e2e-local.sh`、`scripts/build-app.sh`、`git diff --check`。无需为复用的灰色渲染添加截图测试；人工检查同步后列表、置顶区、HUD 一致。

## Acceptance Criteria

1. 新用户导入历史会话不分配特定颜色，显示灰色。
2. 旧用户历史颜色在启动、后台发现或手动同步的下一次统一处理中清空。
3. 近期已有颜色不重分配；近期空颜色按原算法补齐。
4. 历史记录不参与颜色分配评分与占用集合。
5. 有效活动恢复后可重新获得颜色。
6. 不新增独立重置按钮、确认弹窗、到期计时器或数据字段。
7. 会话其他字段与轮播行为保持一致，保存失败可见且写入顺序正确。
8. 必要测试与构建通过；只描述实际验证结果，不承诺未经测量的性能提升比例。

## Out of Scope

- 全量重分配近期颜色、清空会话记录再同步。
- 区分自动和手动颜色来源，保留历史手动颜色。
- 修改颜色距离算法、候选色集、HUD 尺寸、标记形状或列表布局。
- 新增实时到期任务、颜色恢复历史或统计面板。

### 2. 核心接口与执行顺序

建议在 `SessionMarkerColor` 中增加 `historyWindow: TimeInterval = 7 * 24 * 60 * 60`、`isHistorical(_:now:)`，将现有入口改为 `fillingMissing(in:now:)`。`now` 必须为显式参数；编译错误用于查齐调用点，不给默认当前时间掩盖漏改测试。

历史判断等价于：

```swift
let activity = session.lastActivityAt ?? session.lastUpdatedAt
return now.timeIntervalSince(activity) > historyWindow
```

批量函数按以下顺序实现，返回数组顺序与输入一致：

1. 复制输入到结果数组；不修改原数组、不执行文件写入。
2. 使用本次统一 `now` 判断所有记录。历史记录结果颜色设为 `nil`；近期记录颜色调用现有 `normalized`。
3. 收集需要补色的近期记录下标。若为空，直接返回已清理结果。
4. 只从近期有效颜色构造占用集合。不要用原始输入的全部颜色构造集合。
5. 初始化一次现有 `Allocator`，不要对每个记录调用独立的 `allocate` 重复初始化评分。
6. 待补色下标按原有 `rotationIndex` 升序、同值按 ID 升序处理。原有有颜色记录不重新分配。
7. 将分配结果写回对应下标并返回。

禁止错误实现：先为所有记录补色，再把历史显示成灰色。该做法保留了最主要计算开销。禁止把 `#808080` 写入历史记录；灰色由空值回退显示。

### 3. 应用调用点

先用 `rg -n 'fillingMissing|fillMarkerColors' Sources Tests` 查全调用点，包括直接调用核心函数的测试。

- `fillMarkerColors` 改为接收明确的 `now`；内部只修改颜色相关元数据，不修改运行状态或活动时间。更新结果时在当前机器记录上合并颜色，避免覆盖期间已有的其他字段。
- `restoreSessions`：先加载并建立机器，再执行策略、刷新展示。保持现有“结果与原文件不同才请求保存”的逻辑；纯历史空颜色文件无需额外写一次。
- `mergeCodexThreads`：先执行原有导入合并与活动时间最大值逻辑，建立全部机器，再执行策略。不可只对 `threads` 做颜色过滤。空响应也应允许清理当前本地历史记录。请求失败仍走原错误路径，不假装同步成功。
- 手动同步和自动发现都走 `mergeCodexThreads`，不要另复制两套颜色逻辑。不要把后台最近 10 分钟读取范围改成 7 天；读取范围和颜色有效期是不同概念。
- `apply`：保持全部拒绝条件及 `machine.apply` 的接受判定在前。只有有效事件更新机器之后才调用颜色策略。建议对每个有效事件执行统一策略，替换当前“仅当前机器颜色为空时调用”的条件，让有颜色的当前会话也能触发其他历史记录清理。
- Hook 处理中先把更新后的机器写入 `machines`，再分配；后续快照应重新从机器取得，避免使用分配前的局部 `machine` 颜色覆盖当前 HUD。
- 同一次处理尽量复用一个当前时间。异步发现采用结果被处理时的当前时间，不采用网络请求开始时间。
- 不在 `tick`、视图 `body`、标记渲染函数中增加颜色分配。

### 4. 待保存颜色竞争：必须处理

当前 `recordsForWrite` 会用 `pendingColors` 覆盖机器颜色；`finishSessionWrite` 会把成功提交的旧颜色合并回机器。因此仅清空机器里的历史颜色会失败。

推荐沿用现有 `PendingEdit`，不要另建磁盘写入通道：

1. 策略输入需考虑已接受、尚未保存的颜色。构造有效记录时将待保存颜色覆盖到记录，再执行核心策略；否则近期新颜色可能撞上尚未落盘的近期手动颜色。
   实施补充：近期待保存编辑的上次已提交颜色也需暂时占用，因为保存失败后界面会保留它。核心入口增加可选的 `reserving` 集合；应用仅传入近期待保存项的已提交颜色，不传历史颜色。避免新会话分色与失败回退颜色冲突，成功结束待保存编辑后自然释放旧颜色。此规则属于已有“失败保留旧颜色、自动颜色避重”要求的并发补全，不新增用户操作或业务范围。
2. 比较策略结果与有效输入颜色。近期有效待保存颜色未被策略改变时，保持原待保存项，继续原有“成功后发布”。
3. 历史待保存颜色被策略清空时，将其替换为值为 `nil` 的新待保存项，而非仅改机器。`PendingEdit.value` 已是可空字符串，可表示清理，无需修改存储模型。
4. 被策略取代的待保存项必须取得新的 token 和新的 `firstToken`，并转移原 completions 到新项。现有成功回调以 `firstToken` 判断是否有效；若仍沿用旧值，旧写入回调可能恢复已清理颜色。
5. 为这些替换安排后续保存，复用现有 revision/单写入队列。不要丢弃原 completion，不要让调用方永久等待，不要提前报告保存成功。回调代表最终合并操作的保存结果，不保证被后续策略取代的颜色仍保留。
6. 无待保存项的普通历史清理和近期补色可沿用恢复/导入的现有内存更新再保存机制；若为统一性选择全部通过待保存项保存，必须保证首次恢复及 Hook 展示行为仍符合本规范，并覆盖测试。
7. 历史清理未提交时又收到有效 Hook，必须基于新活动时间重新计算。待清理值 `nil` 不能阻止重新补色；必要时用更新 token 的待保存颜色取代清理项。
8. 旧回调被跳过后，不得取消仍有效的新待保存项。保持关闭应用的同步屏障以及 `flushSessionWrites` 等待最终写入的能力。

可采用其他等价实现，但必须通过下表的最终状态和回调断言；不得以“发生概率低”跳过。

| 顺序 | 最终结果 |
|---|---|
| 历史会话手动选色正在写入 → 同步清理 → 旧写入结束 | 最后磁盘和界面为空颜色，旧回调不恢复颜色，等待操作可结束 |
| 历史清理正在写入 → 有效 Hook 重新活跃 → 清理写入结束 | 最后磁盘和界面为近期有效颜色，最新活动时间与运行状态保留 |
| 近期手动颜色待保存 → 同批导入近期无颜色会话 | 新自动颜色避开待保存颜色，手动颜色保存成功后保持 |
| 颜色写入中 → 标题修改或启用状态修改 | 只合并被提交的颜色字段，不覆盖新标题或新勾选 |
| 颜色写入中 → 删除记录 | 旧回调不复活记录 |

### 5. 失败与展示行为

- 核心分配抛错时保留调用前状态，显示现有“会话颜色分配失败”。不要应用半批结果。
- 手动选色保存失败继续保留上次成功颜色；不得把此保证删除来绕过竞争问题。
- 恢复/导入策略沿用现有即时内存更新：如果随后的磁盘保存失败，界面可能已变灰，但必须显示数据保存失败，健康状态阻止继续写入；不得提示“颜色已保存”。不为本次需求另建全量回滚框架。
- 后台或启动保存失败也需要可见反馈，不能只有日志；复用会话数据健康和现有错误消息区域。若使用颜色错误消息，文案应与实际行为一致，例如“会话颜色保存失败，请重试保存”，不要在已更新内存时声称“未更改颜色”。
- 颜色发布后刷新列表、置顶区及当前 HUD 快照；仅颜色变化不调用状态切换或开启新轮播周期。原有发现或 Hook 本身的正常调度行为继续保留。
- 手动给历史会话选色仍允许。直到下一次统一策略调用，该颜色可暂时显示；不在单次手动保存回调里无条件按年龄拒绝所有选色。

### 6. 具体测试输入与期望

核心测试统一使用 `now = Date(timeIntervalSince1970: 2_000_000_000)`；通过相对秒数构造时间，所有调用显式传入 `now`。

| 输入 | 期望 |
|---|---|
| 活动时间 `now - 604799`，已有颜色 | 保留 |
| 活动时间 `now - 604800`，已有颜色 | 保留 |
| 活动时间 `now - 604801`，已有颜色 | 清空 |
| 活动时间 `now - 604801`，更新时间 `now` | 仍清空 |
| 活动时间 `now - 60`，更新时间很旧 | 保留或补色 |
| 活动时间缺失，更新时间 `now - 604801` | 清空或保持空 |
| 活动时间 `now + 60` | 按近期处理 |
| 全部是历史记录，颜色混合有效/空/非法 | 全部为空 |
| 近期手动指定灰色 `#808080` | 保留，此规则不同于历史空值 |

其余必要断言：

1. 混合批次与仅近期批次的近期结果按 ID 比较相同，历史记录即使占据第一候选色，也不影响近期分配结果。
2. 反转输入数组后按 ID 对比结果相同；返回数组本身仍保持输入顺序。
3. 再执行一次结果不变；除颜色外所有字段保持一致。
4. 更新原有 1970 年补色测试：历史场景预期空颜色；另用近期时间保留“旧格式记录补色并持久化”的覆盖。不能直接删除旧测试，也不能把所有旧日期改近期而漏掉历史断言。
5. 保留原有独立距离算法参考测试，只把其记录时间与调用 `now` 对齐，继续验证原分配算法未改变。
6. 集成 fixture 当前 `writeThreads` 固定生成近期时间。增加接收具体线程记录或每条时间的辅助方法，测试手动同步导入新历史、已有历史及近期记录；不把固定时间硬编码到所有集成案例。
7. 自动发现只返回最近 10 分钟记录：使用已有本地历史记录加近期响应，验证未出现在响应中的历史记录也被清理。
8. 启动恢复测试写入临时文件后建立新模型，等待其写入 flush，再重新读文件；避免两个活动模型同时写同一个临时文件。
9. 异步竞争复用 `SessionWriteGate` 控制真正物理写入。无需等待 7 天，可将 fixture 增加初始历史记录输入，在启动清理完成后对历史记录选色再触发同步清理。使用 `defer` 释放闸门，避免测试超时死锁。
10. 文件保存采用 ISO 日期秒精度，比较往返记录时沿用现有 round-trip 方法；不要为毫秒差异放宽颜色或活动时间业务断言。
