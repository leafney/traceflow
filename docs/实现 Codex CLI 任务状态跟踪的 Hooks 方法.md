# Codex HUD 项目开发实现规划

## 一、项目概述与目标

本项目旨在为 Codex CLI 以及基于同一配置目录的 ChatGPT 桌面客户端,构建一个 macOS 原生的悬浮状态监控工具(以下简称 Codex HUD)。核心交互形态是一个常驻悬浮的胶囊 HUD,通过红、黄、绿三种点亮状态与"灯不亮"的默认待机态,配合上下轮播切换,让用户无需持续盯着终端面板,即可感知多个并发 Codex 会话的执行状态(等待人工干预、执行中、已完成、静默待机)。项目采用分阶段推进策略:优先实现 macOS 原生 MVP,充分打磨核心体验后再评估跨平台需求。

整个系统由三个独立组件构成:一个极简的命令行转发器(负责被 Codex hooks 机制调用、转发事件),一个常驻后台的状态聚合与调度服务(维护状态机和轮播算法),以及一个基于 SwiftUI/NSPanel 的悬浮 UI 层。三者职责单一、边界清晰,是后续所有阶段开发的基础架构原则。

## 二、总体技术选型说明

界面与常驻服务统一使用 Swift 与 SwiftUI 开发,悬浮窗口宿主使用 `NSPanel` 配合 `.nonactivatingPanel` 样式而非标准 `NSWindow`,以实现不抢焦点、不进入 Dock 与 Cmd+Tab 的系统级悬浮效果。进程间通信采用 Unix Domain Socket,而非 HTTP 端口,理由是本机场景下无需处理端口冲突与网络权限弹窗,且延迟更低。命令行转发器同样使用 Swift 编写并编译为独立小体积二进制,保证与主 App 技术栈统一,减少维护成本。项目暂不引入 Electron、Tauri 或任何 Web 技术栈,明确将跨平台需求排期在 macOS 版本成熟之后。

## 三、阶段一:验证核心机制可行性(Proof of Concept)

### 目标与范围

这一阶段唯一的目的是验证 Codex hooks 机制在真实环境下的行为是否与官方文档描述一致,不涉及任何 Swift 代码或正式架构搭建。所有验证操作使用最简单的临时脚本和系统自带工具完成。

### 具体任务

在 `~/.codex/hooks.json` 中仅配置 `SessionStart` 与 `Stop` 两个事件,`command` 指向一个简单的 shell 脚本,该脚本读取 stdin 并用 `curl` 将内容原样打到一个用 Python `http.server` 起的临时本地端口,或者直接 `cat` 追加写入一个本地日志文件。之后同时打开三到四个 iTerm2 窗口,分别切换到不同项目目录运行 `codex`,观察并记录每次事件触发时,payload 中 `cwd`、`session_id`、`hook_event_name`、`turn_id` 字段的实际取值,重点验证以下几点:同一项目下多次运行是否产生不同的 `session_id`,不同项目目录下 `cwd` 字段是否准确反映各自路径,`Stop` 事件的实际触发时机是否符合预期(是否在每一轮回复结束后都会触发,而非仅在完全退出时触发)。

如果时间允许,还应额外验证 `PermissionRequest` 事件在触发 shell 命令审批时的实际行为,以及 `SessionStart` 的 `source` 字段在"全新启动"和"恢复会话"两种场景下的取值差异。

### 验收标准与产出物

本阶段产出一份记录了所有实测字段行为的笔记(可以是简单的 Markdown 文本),作为后续阶段状态机设计的事实依据,而不是完全照搬官方文档的字段描述。如果发现任何与文档描述不符的实际行为,必须以实测结果为准调整后续设计。

### 注意事项

这一阶段务必控制投入时间,不要在验证阶段就开始纠结代码规范或架构设计,目的是尽快拿到"地基是否牢固"的答案。

## 四、阶段二:状态机与调度算法(纯逻辑层)

### 目标与范围

在不涉及任何 UI 和进程间通信的前提下,用可单元测试的 Swift 代码实现两个核心模块:`SessionStateMachine` 负责单个会话的状态判定与跳变检测,`CarouselScheduler` 负责多会话之间的轮播排序与抢占逻辑。这一阶段的产出应该是一个独立的 Swift Package,可以脱离主 App 单独编译和测试。

### 状态定义规范

状态分为四种,红色表示需要人工处理(触发源为 `PermissionRequest`),黄色表示执行中或思考中(触发源为 `SessionStart` 白名单内的 `source` 取值,以及 `UserPromptSubmit`),绿色表示一轮任务完成(触发源为 `Stop`),灰色为默认待机态,语义上等价于"三个灯位均不点亮",而非独立的第四种颜色渲染。灰色只能由绿色状态在持续满 10 分钟无新事件后自动降级进入,期间收到任何新事件必须取消降级计时并重新走正常状态跳转;灰色本身是终态,不会自动跳转到其他状态,只能被新的 hook 事件重新唤醒。

计时判断必须基于挂钟时间戳(`Date` 差值计算),不能单纯依赖 `Timer` 的触发时机,原因是系统睡眠期间 `Timer` 不会持续计时,唤醒后需要用真实时间差重新校验,避免因睡眠导致的计时误差。

### 事件过滤规范

`SessionStart` 事件必须先检查 `source` 字段,只有取值属于 `startup`、`resume`、`clear` 时才允许触发状态跳转,取值为 `compact` 时应直接忽略,不更新任何状态或时间戳,因为这是内部上下文压缩触发的技术性事件,与用户交互意图无关。这个过滤逻辑应封装为独立函数,作为后续新增类似过滤规则的统一入口。

如果收到的事件会将某个已处于灰态的会话重新判定为绿色或结束态(例如迟到的 `SessionEnd`),应当只做静默的内部记录更新,不触发插队或视觉提醒,理由是灰态是收尾性的终态,不应因收尾事件本身而制造新的打扰。

### 跳变检测与抢占规范

跳变检测的判定标准是"新状态与旧状态不相等",不区分具体是从哪种颜色跳到哪种颜色,统一走同一套触发逻辑。每次检测到跳变,应将对应会话推入一个先进先出的插队栈,调度器决定下一个展示对象时,必须优先检查插队栈是否非空,非空则按入栈顺序逐个展示,每个至少占满一个完整的展示时长(默认 5 秒),之后才回到常规轮播队列。

常规轮播队列必须实现按优先级分组(红、黄、绿三组,灰态不参与轮播展示)加组内公平轮转的双层规则:红色组非空时只在红色组内部轮转,红色组为空才进入黄色组,以此类推;组内轮转按"最近一次展示完成时间"排序,最久未被展示的优先展示,避免同一组内某个会话被持续压制。每个会话完成一次完整展示后都要更新其"最近展示完成时间戳",作为公平排序的依据。

只有一个活跃会话时,调度器必须能正确识别并跳过无意义的自我切换,不产生多余的重绘或动画触发。

### 时间序防乱序规范

由于 hook 是异步并发触发、不保证完成顺序,状态机在应用任何新消息前,必须比较该消息自带的时间戳与该会话当前记录的最后应用时间戳,只有更新的消息才允许覆盖状态,过期消息应被丢弃并记录日志,不能直接按接收顺序无条件覆盖状态。

### 单元测试要求

必须覆盖以下场景:绿色状态在临界时间点(比如第 9 分 59 秒)收到新事件时不应被误判为已降级;某会话从黄色跳变为红色时,调度器应立即抢占展示且重置计时,而非等待当前展示对象自然结束;短时间内收到两次内容不同但目标状态相同的事件不应被误判为重复跳变而多次插队;插队栈中存在多个待处理跳变时,展示顺序必须严格遵循先进先出;红黄两组长期活跃、绿色组持续为空的情况下,组间与组内的公平轮转规则仍需保持正确;乱序到达的旧消息必须被正确丢弃而不覆盖新状态。

## 五、阶段三:进程间通信与转发器

### 目标与范围

搭建 hooks 触发到主 App 状态机之间的桥接机制,包括一个独立的命令行转发器二进制和主 App 内的 Unix Socket 监听服务,此阶段不涉及正式 UI,可以先用命令行打印验证。

### 转发器开发规范

转发器命名建议固定为 `codex-hud-notify`,职责严格限定为读取 stdin 的完整 JSON、附加一个高精度生成时间戳字段(在读取完 stdin、尚未建立连接前生成,尽量贴近事件真实发生时刻)、连接固定路径的 Unix Socket、写入数据后立即退出。转发器不应包含任何业务逻辑判断,也不应尝试对 `PermissionRequest` 等事件返回 `allow`/`deny` 决策,所有涉及拦截或改写工具调用的场景都不在本项目范围内,只做旁路的信息转发。

连接 Socket 失败时(最常见原因是主 App 未运行),转发器必须快速失败退出,不能阻塞或长时间重试,可选择将失败原因追加写入一个本地日志文件供后续排查,但不应引入复杂的重试或离线队列机制,这部分留作后续可靠性增强的可选项而非本阶段必须项。

转发器的安装路径一旦确定应保持长期稳定,不随主 App 版本升级而改变,因为 hooks 信任是按 hook 定义的哈希记录的,路径或命令字符串变化会导致用户需要重新执行 `/hooks` 走信任审核流程。

### hooks.json 配置规范

配置文件放置在 `~/.codex/hooks.json`,一次性列全本项目需要监听的全部事件类型,建议范围限定为 `SessionStart`、`UserPromptSubmit`、`PermissionRequest`、`Stop`、`SessionEnd` 五种,不监听 `PreToolUse`/`PostToolUse` 等与状态判断无关的事件,避免不必要的性能开销和信任审核负担。所有事件的 `command` 字段一律设置 `"async": true`,理由是本项目只做信息旁路转发,不需要阻塞 Codex 的正常执行流程;`timeout` 统一设置为较短的 3 到 5 秒,用于在 Socket 连接失败时快速失败,避免拖慢用户在 CLI 中的实际交互体验。该配置文件应纳入版本管理,后续如需新增监听事件,应尽量一次性批量调整而非频繁小改。

### 主 App Socket 服务规范

监听服务使用固定路径的 Unix Domain Socket,建议路径为 `~/Library/Application Support/CodexHUD/hud.sock`。App 启动时必须先确保该目录存在,并在重新绑定前检测并清理可能残留的旧 Socket 文件,避免因上次异常退出导致的地址占用问题。收到的每条消息在送入状态机前,必须先做基础的 JSON 解析健壮性校验,解析失败的消息应被丢弃并记录日志,不能导致监听服务崩溃或阻塞后续消息处理。

### 本阶段注意事项

暂不考虑 App Sandbox 与 Mac App Store 上架分发,采用开发者 ID 签名加公证的直接分发方式,从架构上完全绕开 Sandbox 对文件路径的限制。Socket 路径常量应集中定义在单独的配置文件中,便于未来如确需支持 Sandbox 分发时统一切换为 App Group 共享容器路径。转发器二进制即使当前只在自己机器上使用,也建议尽早跑通开发者签名与公证流程,避免因 Gatekeeper 拦截导致 hook 静默失败且难以排查的问题。

## 六、阶段四:UI 层实现

### 目标与范围

基于阶段二、三已经验证稳定的状态机与通信机制,实现胶囊形态的悬浮 HUD 界面,完成上下轮播切换动画与红黄绿灯位的点亮渲染。

### 窗口与视觉规范

使用 `NSPanel` 配合 `.nonactivatingPanel` 样式实现悬浮效果,确保窗口置顶显示、不进入 Dock 与 Cmd+Tab、点击不抢占前台应用焦点。胶囊外观使用 SwiftUI 的 `Capsule()` 裁剪配合系统材质(如 `.ultraThinMaterial`)实现毛玻璃质感,左侧展示会话标题,右侧展示三个灯位圆点。灯位默认渲染为未点亮的低透明度占位圆圈,仅在对应颜色状态激活时填充对应颜色,灰色/待机态即三个灯位均保持未点亮状态,不单独设计灰色填充样式。

轮播切换动画使用上滑过渡效果(`.transition(.move(edge: .top))` 配合 `withAnimation`),默认每个会话展示时长 5 秒,插队展示的会话同样需要占满一次完整的 5 秒时长后才允许被切换,避免用户来不及看清就被切走。

### 标题展示规范

主标题固定采用会话 `cwd` 字段的最后一级目录名,作为稳定且不涉及内容隐私的展示来源;`UserPromptSubmit` 中的 `prompt` 摘要作为可选副标题,仅在用户点击展开详情时显示,不作为默认展示内容。

### 手动兜底交互规范

必须提供点击或悬停展开完整会话列表的入口,列表数据直接复用状态机内维护的会话状态表,按最后更新时间倒序排列,每行展示标题与当前状态颜色,并支持点击某一行手动将其推入插队栈最前位置,作为轮播未及时轮到时的主动查看和干预手段。

### 系统交互健壮性规范

主 App 应监听 `NSWorkspace.didWakeNotification`,在系统唤醒后主动触发一次全量状态重新校验(基于挂钟时间差重新计算是否应降级为灰态),不能仅依赖被动触发的 `Timer`。

## 七、阶段五:调试工具与可观测性

### 目标与范围

在正式功能开发的同时,持续维护一套轻量的可观测性机制,用于日常联调与后续问题排查,不作为独立产品功能对外交付。

### 具体要求

状态机每次处理事件和每次发生状态跳变,都应统一追加写入本地结构化日志文件(建议路径 `~/Library/Logs/CodexHUD/events.log`),日志内容至少包含时间戳、会话标识、旧状态、新状态、触发事件名称。开发调试阶段可直接通过终端持续查看该日志文件的实时输出,验证 hooks 配置与事件触发时机是否符合预期,不需要额外单独开发一套独立的调试客户端。该日志机制应作为长期保留的诊断能力,而非临时脚手架,便于后续版本迭代或问题排查时复用。

## 八、跨阶段通用注意事项

敏感信息处理方面,任何涉及将 `prompt` 原文或其他可能包含密钥、内部代码片段的字段落盘持久化的场景,都应先做基础的敏感信息脱敏处理,内存态展示可以适度放宽要求,但落盘操作必须默认按可能包含敏感信息处理。

性能与资源占用方面,转发器进程的启动与退出必须控制在最小开销范围内,不引入不必要的初始化逻辑,因为它是被 Codex 每次事件触发同步 fork 出来的短生命周期进程,累积开销会直接影响用户在 CLI 中的实际交互流畅度。

配置变更管理方面,`hooks.json` 一旦定稿应尽量保持长期稳定,任何需要新增监听事件或调整转发器路径的变更都应集中规划、一次性完成,减少因信任哈希失效导致用户需要反复执行 `/hooks` 审核确认的摩擦。

跨平台延后原则方面,当前阶段所有技术决策均以 macOS 原生体验最优为唯一优先级,不为尚未确定的 Windows 支持需求预留架构妥协空间;若未来确有需要,应在状态机与调度算法(阶段二产出的纯逻辑层)保持不变的前提下,单独评估使用 Rust 重写通信与状态机部分、搭配 Tauri 实现跨平台窗口宿主的可行性,而不是从项目起始阶段就选择技术上的最大公约数方案。
